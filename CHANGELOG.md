## [Unreleased]

### Added
- **Cross-model review + independent RED test-quality gate + 3-level implementation display.** Three composed capabilities that make review independent of the author (per the 2026 "no output graded by its own model" trust model — Kitchen Loop arXiv:2603.25697):
  1. **Per-agent model config (cross-model review).** `~/.super-dev/config.json` → `agentModels` maps agent roles to `provider/id` models, so `code-reviewer`/`adversarial-reviewer` can run on a *different* model than the implementer. Precedence A: `call.model` > `agentModels[role]` > global `--model`/`SUPER_DEV_MODEL` > inherited session model — a cross-model policy is NOT undone by a one-off `--model`. Resolved per-agent model appears on each `agent … start … model=` log line. Pure `resolveAgentModel` (`workflow.ts`) + `tests/agent-model-resolution.test.ts` (6).
  2. **Hollow- and weak-assertion RED gates (Plan 2).** Tier 1 (deterministic): a RED test file with NO recognizable assertion (`assertionPresenceGaps`, cross-stack) is rejected before the implementer, routed back to `tdd-guide` via the existing RED retry machinery. Tier 2 (independent, cross-model via #1): a `code-reviewer` audits the RED test cases for assertion *strength* (bound to observable behavior vs tautology/stub/impl-detail) — a `weak` verdict re-prompts `tdd-guide`; `strong` proceeds to implementation. Runs every phase. `buildRedReviewPrompt` + `RedReviewData` schema; `tests/hollow-assertion-guard.test.ts` (6) + RED-review WEAK→retry→STRONG case in `implementation-red-loop.test.ts`.
  3. **3-level implementation display.** The implementation stage now renders stage → phase → step: each TDD RED / RED review / Implementation step (and retry) persists as its own nested level-3 dashboard row (`kind: "step"`, 8-space indent) with its own ok/failed glyph, excluded from the top-level stage counter. `tests/dashboard.test.ts` +1.
- **Stage 9 implementation activity banner.** The implementation stage now updates the pi-native phase/working-message banner at each durable per-phase boundary: route specialist, TDD RED generation, RED oracle, RED boundary classification, implementation, build gate, deliverable check, change check, symbol check, post-RED oracle, commit, and summary. The dashboard phase row (`↳ Phase N/M: name`) still owns start/end timing, while the banner shows the current substep with attempt/RED-try detail such as `Implementation — Phase 1/2: Auth — TDD RED (attempt 1, try 1)`. This makes long foreground Stage 9 runs explain what they are waiting on without adding fake nested phase timing rows.
- **Unified verification convergence loop.** The main pipeline now uses one Stage 10 verification state machine instead of separate review and integration loops: every attempt starts with fresh code-review + adversarial-review + deterministic build evidence, integration runs only after those pass, and any review/build/integration fix forces the next attempt to restart at review before testing again. Terminal success now requires review approval, build green, and integration passed (or explicit no API/UI surface) on the same final code state; budget/stagnation exhaustion stops before applying an unreviewed final fix. The run state records per-attempt local timestamps, durations, review/build/integration outcomes, failure signatures, code-state hashes, and fix-change evidence under `__verificationAttempts`. Integration tester side effects are guarded by the same hybrid boundary approach as RED tests: obvious test/runtime artifacts are allowed, ambiguous paths go through the LLM boundary classifier, and production-file writes stop the loop without routing the problem to the implementer. New focused tests cover review-fix-review-integration, integration-fix-review-integration, no final unreviewed fix, and tester production-write rejection.
- **Implementation symbol/hollow-file gate — kills the "silent-empty-success" failure mode.** A new `computeSymbolGate` (`src/build-runner/gates.ts`) is AND-ed into phase-green alongside buildGate/deliverableCheck/changeGate: a claimed source deliverable that EXISTS (so it passes the deliverable + change gates) but contains NO language symbols (doc-comment-only / empty shell) now FAILS the phase, with the hollow files fed into the next implementer retry. Catches the exact failure observed in run `2026-07-28T13-59-52` (Phase 3 shipped as ~1.5KB doc-comment-only shells while the summary claimed "3/3 complete", triggering a ~49min review-fix loop + a stagnation break). Language-aware symbol probes (rust/go/python/ts-js) over comment-stripped source; never throws and degrades to pass on unreadable files / unknown language / phases with no source files (never blocks infrastructure or doc/config-only phases). New: `tests/symbol-gate.test.ts` (9); stub added to the 2 explicit build-runner test mocks. `npm run typecheck` strict-clean; full vitest suite green (1527 tests).
- **HITL escalation: super-dev now ASKS the user (ctx.ui.select) when it hits an unrecoverable blocker, then continues based on their decision.** An escalate(failure) callback is threaded from extension.ts -> RunOptions -> StageContext and fired inline at gate exhaustion (nodes.ts) + verify-loop stagnation (verify.ts) BEFORE the abort. Interactive: ctx.ui.select with options (retry-with-guidance / accept-limitation / abandon) + ctx.ui.input for guidance. Retry: rollbackWorktreeTo + appendUserNotes -> stage re-runs with guidance. Headless: report + fail. Default-on in TUI/RPC. Never throws; bounded by ESCALATION_RETRY_CAP=2. typecheck clean; 1574 tests green.
- **Mid-run user context: type during a super_dev run and it's captured + persisted for every subsequent stage.** Free-text typed while the pipeline runs (in BOTH foreground and background modes — previously the background default discarded it) is now captured and appended to a durable `<specDir>/.user-notes.json` (mirrors `.knowledge.json`: cleared at pipeline start, kept on resume, never read by agents — the pipeline injects it). Each specialist's prompt gains a `## User context (added during the run)` block carrying all notes accumulated so far, so context added mid-run reaches every remaining stage. Slash-commands (`/super-dev-stop`, `/reload`, …) still pass through unchanged. Delivery is non-interrupting (picked up at the next agent boundary, like pi-subagents' file-backed steer queue). The fragile live-steer path (`session.steer` / `onSteer` / `makeSteer` / `SteerSink` / the `activeSteerForwarder` state + setter) is REMOVED — the durable file + between-agent drain is the sole delivery contract; `applyThinkingLevel` is intentionally kept. New: `src/render/user-notes.ts` + `tests/user-notes.test.ts`; rewritten `tests/workflow-user-steer.test.ts`; updated `tests/input-handler.test.ts`; removed the two live-steer test files. Independently reviewed (approved, no blockers/issues). `npm run typecheck` strict-clean; full vitest suite green (1518 tests).
- **Inherit model settings while isolating ambient agents/extensions via explicit role extensions + excludeTools (spec-17 follow-up).** Specialist `pi` agents now keep ambient discovery disabled by default in BOTH backends: subprocess uses `--no-skills --no-extensions --no-context-files --no-prompt-templates`, while the session backend uses `DefaultResourceLoader({ noExtensions: true, noSkills: true, noContextFiles: true, ... })` plus empty AGENTS.md/CLAUDE.md overrides. This keeps repo-bundled `agents/<name>.md` as the sole role definition and prevents installed packages such as `pi-subagents` from discovering `~/.pi/agent/agents` or project agents. Research/browser capabilities still work through explicit `-e` role extensions only (`pi-web-access`, `pi-mcp-adapter`, `pi-browser-cdp-extension`). Recursion remains blocked by `excludeTools: ["super_dev"]` / `--exclude-tools super_dev`, and subprocess agents now receive a generated `<control>` contract from `controlKeys` plus one corrective retry when the control block is missing or incomplete. `tests/pi-spawn.test.ts` pins the isolated argv and role-extension behavior.

- **Stage 9 implementation deadlock: RED author now receives the exact `requireTests`/`requireFiles` deliverable contract, and `missing test:` deliverables route back to RED regeneration instead of the forbidden implementer.** Root-cause of run `2026-08-10T10-54-20-663Z` (only 1/3 phases implemented, Phase 2 stopped as `no-progress`): the RED-phase author (`buildTddPrompt` → `tdd-guide`) was graded by the deterministic deliverable gate on `phase.deliverables.requireTests` *name strings* but was never told those names, so it named `it(...)`/`test(...)` cases freely and the gate reported `missing test: <name>` on every attempt. The only agent allowed to add tests afterwards — the implementer — is forbidden from touching RED files (`tdd-tests-modified-during-green`), so the two gates were mutually unsatisfiable and the phase failed after the no-progress cap, abandoning all later phases. Fix: (1) `buildTddPrompt` now renders a `## Required Deliverables` block listing every `requireTests` name (to author verbatim) and `requireFiles` path, so the RED phase produces the graded names up front (context-over-procedure, per arXiv:2603.17973 "TDD prompting paradox"); (2) a `missing test:` deliverable now invalidates the accepted RED and re-runs `tdd-guide` (which receives the names) rather than instructing the implementer to add tests; (3) both implementer-facing retry blocks exclude `missing test:` items so the prompt never asks for the forbidden action. - **Stage 10 review convergence now honors review-finding taxonomy.** Review and adversarial findings now carry status/blocking/confidence/evidence/recommendation through the prompt, rendered markdown, convergence ledger, verdict merge, and local stagnation detector. Verified/addressed/deferred findings and explicitly `blocking:false` findings no longer trigger another blind fix or a false recurring-blocker stop, even when they reuse an earlier high-severity finding id to confirm the prior issue is fixed. `Changes Requested` is downgraded to `Approved with Comments` when every structured finding is non-blocking, while open high/critical findings, explicit blockers, `needs-human`, `REJECT`, and `Blocked` remain merge-blocking.
- **Stage 10 verification no longer false-stops on count-only finding growth, and docs cannot mutate source after a blocked review.** Verification convergence now records merged review findings into the convergence ledger and uses per-blocker fingerprints for stagnation: a run like `8 findings -> 9 different findings` continues, while an actually recurring blocker after targeted fixes stops before another blind fix. Fixer prompts now preserve review finding id, file, line, detail, evidence, recommendation, and owner stage instead of reducing them to severity/title, so Stage 10c receives actionable repair context. Stage 12 documentation now runs with `source-read-only` access, its prompt/agent contract prohibits production-source and project-level doc edits, and the main pipeline only runs docs, pre-merge build, cleanup, and merge after Stage 10 has positively verified implementation with review approval, build pass, and integration pass/not-applicable proof.
- **Stage 9 implementation convergence is no longer hard-capped at five local attempts.** Implementation and RED generation now run while the global run budget allows, but stop when the same actionable failure repeats with the same change footprint. TUI activity labels now show absolute `attempt N` / `try N` instead of `attempt N/5` / `try N/5`, RED retries log `retry N` without a denominator, and terminal run-log lines explain whether Stage 9 stopped for repeated no-progress or budget exhaustion. The outer Stage 9 convergence node also no longer uses `SUPER_DEV_MAX_CONVERGE_ITERS`; it re-enters only until all phases are green, the budget is exhausted, or Stage 9 reports a no-progress block. New regressions prove repeated identical failures stop after feedback, while changing deliverable evidence can continue past the old fifth attempt and succeed on attempt 6.

Stage 10 run-log lines now show `attempt N` and `integration retry N` without `/5`, budget exhaustion replaces max-attempt terminal findings, and prototype rounds log `round N` while stopping on repeated identical prototype evidence. Low-level `retry()`/`gate()` primitives and transient API retry backoff remain explicitly bounded when a caller opts into them.
- **Budget-bounded artifact/spec ambiguity convergence.** Requirements, BDD, research, and spec/review now run as clarity-convergence loops bounded by the global run budget/cancellation/non-retryable environment failures instead of local `5`-attempt caps. Requirements now fail unresolved `openQuestions`, BDD keeps retrying until every AC is covered, research treats prior `openIssues` as the next search agenda, and spec/review feedback no longer says `attempt N/5`. New regressions prove requirements, BDD, research, and spec can all pass on a sixth convergence round.
- **Package/runtime version alignment.** The runtime extension version now uses npm-valid semver (`0.1.21`) and `package.json` / `package-lock.json` track the exact same value. The session backend uses a read/diagnostic tool allowlist plus `edit`/`write` exclusion, the subprocess backend excludes the same tools, and the workflow runner takes a git-status snapshot around each source-read-only child call. Mutations under the active spec artifact directory remain allowed for report artifacts, but source/config changes outside that directory fail the agent call; clean tracked files and new untracked files are restored automatically, while pre-existing dirty files are reported for manual handling to avoid overwriting user work. A new shared ledger records finding id, owning stage, status, blocking flag, evidence, invalidated downstream stages, and local timestamps. Spec review findings must classify `ownerStage` and prior finding resolution, spec rewrites include `reviewResponses`, and the workflow runner injects open ledger findings into later retry prompts unless a stage already supplied them. Environment failures such as `spawn pi ENOENT` are classified as non-retryable and stop fatal gates after one attempt with PATH/cwd diagnostics instead of burning all retries. Stage 9 and verification terminal blockers also write ledger findings, and the spec trace gate now catches a concrete Next.js catch-all-vs-specific-route grounding error before implementation. Regression coverage includes spec finding carry-forward, upstream owner routing, non-retryable gate stop, shared runner injection, route grounding, and a `/tmp` smoke that carries a spec-review finding into a Stage 9 TDD implementation of a tiny `multiply` feature.

Prototype retry rounds, subprocess corrective control-output retries, and in-process session `structured_output` corrective re-prompts also use the same location/observed/expected/missing/next-action contract. A failing-but-incomplete RED suite is recorded as `coverage-incomplete`, logs the missing `SCENARIO-NNN` IDs, writes that status to `implementation-evidence.jsonl`, and retries `tdd-guide` with a compact missing-scenario repair block before any implementer can run. - **Stage 9 retries now reuse accepted RED tests and repair the failed GREEN boundary.** Once a phase has a valid RED oracle, build/deliverable/symbol/post-RED failures go straight back to the implementer with the concrete failure evidence instead of starting a new `tdd-guide` run. The RED cache is invalidated only when the implementer edits confirmed RED test files, at which point TDD is run again. - **Stage 9 activity banner stays visible under live-stream compaction.** The latest `▶ Implementation — Phase N/M: ... — <activity>` banner is now treated as the current implementation activity anchor, so a long-running TDD/implementation/build agent cannot push the substep indicator out of the running stage section. Older activity banners still compact normally; the full run log remains complete.
- **Stage 9 RED generation now gets real runner diagnostics instead of blind `broken` retries.** The RED oracle now emits per-command diagnostics (`cwd`, argv, classified status, exit code/signal, spawn error, bounded stdout/stderr tail) through an additive `onResult` callback. Stage 9 logs those diagnostics, persists them in `implementation-evidence.jsonl`, includes the first diagnostic in RED failure reasons, and injects the runner tail into the next `tdd-guide` prompt when RED is `broken` or weak-green. RED-generation exhaustion is now logged truthfully as “stopped before implementation” instead of pretending the implementer failed five times.
- **Repeated Stage 9/phase convergence attempts now render as separate foreground occurrences.** The extension keeps workflow/resume IDs unchanged, but the foreground stream/dashboard assigns display occurrence IDs (`#2`, `#3`, …) when a stage or phase starts again after a terminal status. Re-entered phases get fresh start/end timing brackets and labels like `(attempt 2)`, so a failed first convergence pass and a later successful retry no longer collapse into one misleading Phase 1 section with a combined duration.
- **Path-derived module ownership for implementation gates.** The deterministic build gate, RED oracle, and deliverable `requireTests` checker now derive the owning project/module directory from touched files and declared deliverable paths instead of assuming the repository root. Build verification keeps the root gate when present and additionally runs touched nested modules from their own cwd; nested Go modules now run `go mod download`, `go build ./...`, `go test ./...`, and `go vet ./...` from the module directory instead of returning green with `ran: []`. The RED oracle can run nested Go targets from their owning `go.mod` directory and classify real Go failures as RED. The deliverable test lister now plans per cwd+argv, merges root and owning-module test lists, and fails missing named tests in nested packages instead of degrading to `tests:unavailable`. New regression coverage: nested Go build-gate planning, nested Go RED planning, and nested Vitest `requireTests` positive/negative cases.
- **Build gate now executes touched nested Node modules from their module directory.** The deterministic build gate still runs the root commands, but for Node workspaces with nested `package.json` files it also resolves touched module directories from git and runs their `build`, `test`, and `typecheck` scripts with `cwd` set to that module. Nested packages inherit the root workspace package manager when they do not declare their own, and run labels include the module path (for example `auth-service: pnpm run test`).
