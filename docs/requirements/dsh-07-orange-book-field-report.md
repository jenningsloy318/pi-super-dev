## 1. Overview: what the Orange Book is and why it is a distinct evidence class

The official dsh repo documents what the product **is** (architecture, subsystems, Agent Notes). The Orange Book documents what the product **does to a real machine and a real wallet in the first 24 hours**, written by a user who represents the exact "AI-native builder" persona the harness marketing addresses but who has never written a line of code. The book's stated stance: 讲清楚「它是什么」是官方文档的活；这本书只写我在自己这台电脑上跑出来的东西，包括它做错的、没做完的、文档跟实际对不上的地方 (§Prologue) — "official docs own what it is; this book only records what I ran on my own machine, including what it got wrong, left unfinished, and where docs contradict reality."

The book's structural signature is a recurring end-of-chapter column, 《他们本来想这么做，后来没做》 ("They wanted to do X, then didn't") — a direct consumer-grade reading of the repo's rejected Agent Notes (§5 of this report lists every concrete example the book surfaces).

Three meta-findings frame everything below:

1. **The book is falsifiable by design.** Every number ships with the command that produced it (book §99 appendix: 每一个数字后面都跟着取数命令 — "every number is followed by its command"). Spot-verification during this analysis confirms the book's numbers against the current repo: preset file line counts 251/262/262/62 (`apps/cli/config/agent-presets/{standard,code,cordis,minimal}/agent.cordis.yml`), 27 non-test verify gates (`ls scripts/verify-*` = 35 files, 27 after removing `.spec` tests), 215 package READMEs with a `KV Cache effect` section, 219 `invariant.ts` companion files of which 184 carry `No runtime invariant:` explanations, exactly 11 English rejected notes, 4 postmortems numbered 0001–0004.
2. **The book itself corrects its own errors in-print** (§04): the author initially wrote that 35 out-of-tree packages were "not shipped with the product," then discovered all 35 return HTTP 200 on the npm registry and rewrote the claim, keeping the retraction visible — 我差点把死路写进书里 ("I almost wrote a dead end into the book").
3. **The book's shelf-life honesty** (§99 保质期): "if your run differs from the book, trust your run" — because at snapshot time the npm package walked through four versions in one day, and the author found three separate doc-vs-code contradictions (including one where a stale tool name is baked into a **model-facing** skill file, which is worse than a stale human doc because it misleads the model itself).

## 2. The author's methodology

- **No-code author as an asset, not a limitation.** Every mechanism is explained via a daily-life analogy (Lego car, courtroom stenographer, customs declaration form) AND each analogy ships with an explicit 失真处 (where the analogy breaks) — e.g. the "harness = kitchen" metaphor is corrected to "a real electrician doesn't read the ladder manual aloud before every sentence, but the model re-reads 25 tool manuals every turn."
- **Everything first-hand and reproducible**: installs, permission walls, cost measurements, the self-tool-creation run, hooks, MCP, and the Claude Code subagent delegation were all executed on the author's machine; the book explicitly marks what was NOT run (e.g. §09 Ralph loop: 这套循环我一次都没实跑过 — "I never ran this loop once"; §11's "disable the agent-loop row" thought experiment: 这一条我没有实跑验证过).
- **Log archaeology over trust**: the author's core technique is decompressing `~/.dsh/sessions/*/session-*/session.jsonl.zstd` (`zstd -dc … | python3 …`) and reading the actual request envelope, which is how the book recovers the full system prompt, the tool list, and the per-item cost table without any decompilation or packet capture (§05: 没有反编译，没有抓包，没有问官方要 — "no decompiling, no packet capture, no asking officials").
- **Number provenance discipline**: the count `44` appears twice with different meanings (44 file lines vs 44 event types — explicitly flagged as coincidence); three different `184` numbers in the book are cross-checked and declared unrelated coincidences.

## 3. The four-questions-at-the-door framing (§00)

The prologue answers the four questions a non-coder asks before installing an agent that can touch their machine, replacing marketing copy with measured facts:

1. **要不要钱 (Does it cost money)?** Yes, and structurally differently from Claude Code/Codex: all four credential layers are API keys; the repo contains no concept of a subscription (订阅), so "nothing will stop you before you overspend." Measured anchor task (read 4 files, run a verification, write a README): deepseek-v4-flash $0.0034 / 35.7s; deepseek-v4-pro $0.0097 / 45.4s. (Official time-of-day pricing change announced for 2026-08-17.)
2. **我的东西会不会传出去 (Will my stuff leave the machine)?** Three-part answer: process local, conversation leaves (files you ask it to read must be sent to the model); telemetry off by default; **but** one thing cannot be turned off — after first auth the machine generates an anonymous UUID that rides every request to DeepSeek regardless of the telemetry switch, disclosed by dsh itself in the owning package README's "Known Limitations" section (book: 这条不是谁挖出来的，是他们自己写的).
3. **它会不会弄坏我的电脑 (Will it break my machine)?** Risk judged "controlled" via the three-tier sandbox (read-only / workspace-write default / full-access with confirmation) plus an ask-based approval policy; the gap stated plainly: the three-tier vocabulary governs **files only, never network** — an officially documented blank, not an oversight.
4. **那道四选一 (The mode four-way choice)**: the author simply answers it for the reader — use Standard mode; the other three are not "better standard modes" (they are a different invocation style, a benchmark rig, and a meta-mode that produces new modes). Key trap: modes can only be switched while a session is blank, because "once a turn has run, that history was produced under the preset's tools and swapping them would strand logged tool calls" (quoted from an internal engineering note in the book; mechanism §4.4 below).

## 4. Mechanisms: what the book measured, at code level

### 4.1 The 129-line boot manifest (§11)

`dsh --profile web --dump-default-config` on the author's machine prints 490 lines of YAML; the plugin skeleton is 129 rows, one package per row. The book's reading:

- Row one is `timer` (`@deepseek-ai/cordis-plugin-timer`); the **agent main loop is a sibling row** (`- id: agent-loop / name: '@deepseek-ai/dsh-agent-loop'`) with identical format and identical provenance markers — "your agent is not a program, it is a 129-line list."
- The dump annotates every row's origin: `# == @deepseek-ai/dsh-base` and `# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app` (24 provenance markers, 25 rows marked disabled in the author's dump) — composition is inspectable without reading source.
- The composition algebra (verified against repo docs `docs/architecture.md` §Profiles and bundles): empty list `[]` → base bundle patch (78 plugin rows) → web-app bundle patch → profile `cordis.patch.yml` → home-level patch → `--patch` overlay. Patches target rows **by id and replace the whole row** (no deep merge) — deliberately: any row's final effective config is readable in one place.
- 133 plugins running at runtime vs 3 configurable cards in the settings page — the book names this gap as the product's current most-criticizable surface, and notes the split (composition belongs to config files; runtime preferences belong to settings) mirrors where Codex/Claude Code/Kimi/OpenCode converged per dsh's own architecture notes.
- The web UI itself grows on the same tree: ~27 `ui-*` rows in the manifest (typert remote-call mechanism, repo doc `docs/subsystems/typert.md`; design note `.agents/notes/implemented/architecture/2026-08-02-typert-remote-method-calls.md`).

### 4.2 The full system prompt and the request envelope (§05, §06)

Because every request envelope is snapshotted into the log as `request/header` + `request/context` events, the book extracts, verbatim:

- The **Standard-mode system prompt: 4,100 characters**, beginning `You are an AI agent powered by DeepSeek Harness.`, containing behavioral rules such as "use the read tool for text files, not shell commands like cat," "check the exit-code marker on every bash result," "remember background job ids, don't busy-wait, don't re-run."
- The **25-tool manifest** (both web-standard and headless lists are 25 — explicitly flagged as coincidence; headless includes `str_replace_editor`, web includes `ask_user_question`).
- The author's own **skill catalog injected verbatim**: 16,542 characters of 57 skill name+description pairs in one `user/message`, zero configuration performed.

The load-bearing product invariant the book isolates (repo phrasing "Model-visible means logged", `docs/architecture.md` §Session log): anything reaching a model request must be reconstructable from the log, and a **runtime check compares the outgoing message list against the re-derived list before every request and throws on mismatch** (six fields compared: model, system prompt, temperature, output cap, tool list, messages). The book's gloss: 「我没有偷偷给模型看别的东西」这句保证每次发请求之前都要被代码自己比对一遍 — "the promise 'I'm not secretly showing the model anything else' is machine-checked before every request, not written in docs for you to believe."

### 4.3 The 44-event session log: 3 model-visible, 41 audit-only (§05)

A one-line Chinese task (用一句中文说明当前目录下有哪些文件) leaves a 44-line log file (125 numbered events after unpacking packed rows): `assistant/chunk` fragments, packed rows (≥3 consecutive fragments compress to one line), 3 `user/message`, 2 `assistant/message`, turn/step boundaries, inbox splice events, title events, `tool/call`+`tool/result`, 2 `request/*` envelope snapshots, and the 3 permission rows (`permission/preset`, `sandbox/mode`, `approval/policy` — the session's permission state is journaled as facts, so "what permissions was it under when it changed that file last week" is rewindable, not a memory).

- **Only 3 of 44 event types are model-visible** (user message, assistant message, tool result) — the rest exist for humans and audit. Book analogy: a courtroom transcript vs the jury hearing only witness/lawyer/evidence.
- The projection model: model history is **re-derived from the log at every request** (`deriveMessages()`), so "model forgot" and "log lost" are different failure classes.
- Fork/resume/replay are three reads of one mechanism (fork = copy the log prefix as a seed, cut only on whole-turn boundaries; resume = whole log as seed; replay = a real log as a script with **no API key needed** — dsh's internal test facility, meaning a crash scene is packageable and reproducible).
- Compaction **never deletes originals** (§05): compacted events stay in place in the log; a new summary message records "I masked items N..M" plus which model wrote it and its token budget — opposite of the usual /compact behavior. Three cost-tiered mechanisms disambiguated: spill (oversized tool result → file, model keeps a path; free), prune (mechanical mid-section truncation; free, permanent), compact (LLM summary; costs a model call). The book live-verified spill+prune (a 171,000-byte `cat` truncated to the 50,000-byte cap with a two-line pointer, byte-exact: 14,385 omitted), and honestly marks compaction as not reached in its runs.
- Costs of the log: an echo task leaves 35 physical records; no retention policy by decision ("本决策不引入任何保留期策略"); format version 0 refuses old logs without migration; and append-only means you cannot surgically erase one sentence — the book flags this as a real privacy trade (设计，不是疏漏 — by design, not an oversight).

### 4.4 Modes are four folder manifests (§03, §08)

The four modes are not switches but four composition files (verified line counts): standard 251, code 262, cordis 262, minimal 62 (`apps/cli/config/agent-presets/*/agent.cordis.yml`). Switching mode = swapping the manifest; the blank-session-only rule exists because tool-schema swaps would strand already-logged tool calls. The only supported way to create a fifth mode is **copy an existing one and edit** (rationale in §5 rejected-designs). Two extra gotchas the book caught by hand: selecting a workspace silently resets a previously chosen mode back to Standard (undocumented ordering trap: workspace first, then mode); and minimal mode is Windows-unusable (hard-binds bash; the only preset without platform gating — tracked as a repo TODO).

### 4.5 PTC mode (Code mode) and the counterintuitive cost finding (§08)

PTC (the letters exist only in the Chinese UI; the repo never expands the acronym anywhere in ~200k lines of code and ~2k docs — 来历不明, "origin unknown"; English name Code mode, directory `code/`) lets the model write one TypeScript program per turn calling tools as ordinary async functions (`run_code` is the single visible tool).

- **The customs-form move**: the 25 tool definitions do not shrink — they move from the tool-parameter table (26,894 → 897 chars) INTO the system prompt (4,101 → 35,643 chars). Same bytes, different envelope position. Net first-turn input: 13,842 (standard) vs 15,040 (PTC) — **fixed overhead UP ~9%** on the measured task.
- **What it actually saves**: intermediate results. In the PTC run the model invoked tools 5 times (all `run_code`) while those programs dispatched 15 real operations (3 glob, 3 bash, 5 write, 4 read); the 10 intermediate outputs never entered the model's context (they land as code-dispatch events in the log — model-invisible, human-auditable).
- **The same-model same-task A/B** (V4-Pro, max reasoning, 3 small files, identical prompt): standard 4 steps / 7 tool calls / 14,447 new-input tokens / 1,416 output (739 thinking) / 21.9s; PTC 6 steps / 5 calls / 17,591 new input / 17,235 output (**13,095 thinking, 76%**) / 305.9s. Book verdict: on small tasks PTC is comprehensively more expensive; it is a bet that pays only when "the work's middle produces large outputs the model never needs to see." The author's honest scoping: single run, no repeats — "I can say 'on my three-file task it was ~14x slower', I cannot say 'proven PTC is 14x slower'."
- **The enforcement lesson** (book cites the 2026-08-07 fix note): PTC initially restricted only the *broadcast* surface (one tool schema sent) while the executor still accepted direct native-tool names — 模型只要直接喊出一个原生工具名，调用照样穿过管线执行了. Fix: block at the executor, with a rejection message that explains the way home ("only run_code may be called directly; call the others inside your program") because a bare "unknown tool" reads as a deployment breakage, not a correction. Book contrast: Anthropic documented the same hazard as a warning; DeepSeek enforced it in the executor.
- **State sharing deliberately rejected**: each program runs in a fresh isolated environment because cross-call state would be invisible to the session log and break "every request is a pure function of the log" — the book flags this as the exact point where dsh and Anthropic's code-execution interface walk in opposite directions (one bets rebuildability, the other bets performance).
- The model's actual programs shown: it self-writes JSON file-passing to avoid shell quoting, runs Python for computation and re-consumes results in JS, and self-verifies (re-reads its own report, discovers the "largest file" tie and that its own report file pollutes the next statistics pass — a self-reference hole humans also miss).

### 4.6 Creation mode: the model building its own 33rd tool (§07)

The book's centerpiece live run (§00 prologue hook): in Creator mode (English "Creator mode", directory `cordis/`), one prompt asked the agent to inspect its own runtime then **build, mount, and immediately use** a `count_chinese` tool.

- Result in 3+ minutes, zero further human input: services 55→55, model-visible tools **32→33**, dynamic plugins 0→1 (`cjk-1`); `count_chinese("探索未至之境")` → 6 (correct).
- **19 steps / 24 tool calls; the first 14 steps and 20 calls did nothing but read its own documentation**: 6× runtime introspection (`cordis_inspect*`), 6× filesystem exploration of its own install dir, 4× type-declaration reads (`.../@deepseek-ai/dsh-tools/lib/types/types.d.ts` — "an agent reading the spec sheets of its own parts in order to install itself a new part"), 3× greps for `defineTool`, and 1 self-discovered load of the `cordis-plugin-development` skill. Only the last 4 calls did real work (submit definition, mount into the live runtime, confirm 33, use it).
- The 20-line plugin (reproduced verbatim in the book) shows the quality payoff of read-before-write: its CJK regex covers **three** Unicode ranges (extension A, common, compatibility) where a from-memory version would write one; the extra two ranges are never exercised by the test sentence.
- The log proves the mid-conversation mutation: exactly 2 `request/header` snapshots, `initial 32` and `change 33` at step 17 — the tool list changed **mid-turn**, automatically journaled. The book: this is "everything is a plugin" fulfilled most literally — insertion happens during the run.
- **Boundary**: dynamic plugins live only in process memory; five official "not"s (creates no files, installs no packages, changes no config, does not survive restart, cannot auto-promote to a real plugin). Risk label from dsh's own preset file: treat the session as "you handed over the command line" (the sandbox isolates globals but is 不是安全边界, not a security boundary), because the model's code is evaluated against the live runtime.
- Doc-drift catch: the preset's bundled guide names **five** introspection verbs; the runtime exposes **seven** (the "inspect" verb was split into three). The book's rule: wherever tool names appear, trust the measured runtime over docs.
- The book's synthesis with the JY quote: this is a prototype of 自我进化软件 (self-evolving software) — 它能给自己长出一只手，但这只手活不过一次重启 ("it can grow itself a hand, but the hand does not survive a restart"). And the author's structural reading of why promotion is blocked: allowing the agent to persist self-modifications would extend the "model-visible means logged" invariant across sessions and into the config directory, at which point "what this agent is" is no longer answerable from one log.

### 4.7 "What is it allowed to touch": permission experiments (§02)

The book ran the full permission chain on its machine:

- The first three log rows of any session are the permission triple (`permission/preset: workspace-write`, `sandbox/mode: workspace-write`, `approval/policy: ask`) — default state is journaled, not implicit.
- Two independent knobs packaged as one selector: sandbox tier (read-only / workspace-write default / full-access) × approval (ask / never; never = deny-on-escalation, and in factory presets never is only paired with full-access where nothing needs escalation).
- The escalation card **replaces the input box** (not a modal): model-written justification (unbounded, scrolls), command text in monospace, exactly two buttons — 拒绝 / 允许一次. **No "always allow," no rule memory, no whitelist** — the same command asks again next time. Buttons live outside the scroll region so a long command can't push them away.
- Four distinct rejection phrasings the model receives (user rejected / approval canceled / no approval channel available / no approval service composed) — deliberately different so the model knows whether to replan or give up.
- **Refusal semantics are absolute**: after 拒绝 the command never ran — no partial output exists; and for unattended runs, nobody answering equals deny (absent, exception, out-of-vocabulary answers all classify as unavailable → treated as rejection; 设计，不是bug).
- The kernel-level escalation ladder shown to the model after a denial: `[sandbox: file access denied under workspace-write mode]` + `[sandbox: escalation available — retry this exact operation once with sandbox_permissions (the narrowest wider mode that suffices) + justification; the approval prompt asks the user]` — three gates: strictly-wider-only (a non-widening request is bounced at execution without bothering the human), read-only is the floor, and **one retry in the same turn** — 升权从不投机 ("escalation is never speculative").
- OS-level truth: macOS `sandbox-exec`, Linux bubblewrap→Landlock fallback, Windows restricted tokens; explicitly **not** seccomp (only two repo mentions, both in a rejected note). The Linux launcher is ~300 lines of C that handcuffs itself before exec'ing the target — 焊死的门, a door welded from inside; even fully-compromised arbitrary code stays in the circle because the restriction lives in the kernel. Three honesty caveats: a "partial enforcement" tier exists and is reported honestly; network is entirely outside this vocabulary (designer-stated blank); and the macOS tool is deprecated-with-a-probe: if it disappears, dsh refuses to run rather than silently deprotecting.

### 4.8 Cost accounting methodology (§06)

- **The entry fee**: first-request miss input = 13,838 tokens, decomposed by differential weighing (send each block to the API with `max_tokens:1` and read `prompt_tokens` from the receipt): 25 tool manuals 6,510 (47.0%), the author's own 57-skill catalog 6,242 (45.1%), system prompt 844 (6.1%), runtime snapshot 129 (0.9%), protocol overhead 82 (0.6%), **the actual question 29 tokens (0.2%)**. "I asked a 29-token question; the harness prepaid a 13,809-token entry fee."
- **45% of the entry fee is the user's own assets** — the skill pool read zero-config from `~/.agents/skills` raises per-session entry cost from ~7,600 to 13,838 (+82%), paid **per new session and per subagent**, with zero skills used in the measured task.
- **Cache economics**: flash cache-hit price = 1/50 of miss (pro = 1/120). The 5-step task: step 1 all-miss 13,838; steps 2–5 mostly hit (267/786/319/177 miss); 80.4% hit rate; all hit counts are multiples of 64 (verifying DeepSeek's documented 64-token cache granularity). A fourth run in a **new process and session** 2m21s later hit 13,824/13,838 of the entry fee — cross-process prefix cache. Book's anti-hype correction: "50x cheaper" is unit price only; with output tokens undiscounted, a full cache-miss run is 3.55x, not 50x.
- **KV-cache as enforced writing discipline**: every package README must end with a `KV Cache effect` section classifying its behavior (append-only / stable repeating prefix / replaces earlier content / independent request) and naming what breaks reuse — 215 of 219 packages filled it, 4 whitelisted with reasons written inside the gate script itself (`scripts/verify-*` family). Book-extracted practitioner rules: don't change config/persona/tools mid-session; paste images at the start; even tool reordering (same content) drops the cache.
- Three practical traps measured: a web-UI model dropdown click writes a shared settings file that **overrides the CLI flag silently** (author's CLI flash run was billed as pro, 3x); the product itself never converts tokens to money anywhere in the repo; and the context gauge assumes 4 chars = 1 token (Chinese measured at 1.71 chars/token, so a 40% gauge reading can be ~90% actual).
- Benchmark literacy (§06/§14): "105x cheaper" headlines measure **model** price; harness cost is what Composio measured (same model, 8 harnesses, 240 runs: pass rates 46.7%–66.7%, ~7x cost-per-success difference) — the two numbers are independent and must not be multiplied.

### 4.9 Out-of-tree packages: "repo has it" ≠ "installed has it" (§04, §99)

- 219 repo packages; 184 in the default install closure; **35 published to npm but not auto-installed** (subagent providers for Claude Code/Codex, hooks bridges, ACP, Python SDK/remote invocation, LSP, cloud sandbox, SQLite backends, search swaps, real interactive terminal…). All 35 verified live on the registry (HTTP 200, checked one by one) — the author's own first-draft error ("not shipped") is retracted in print.
- **The `@next` trap**: the other packages' `latest` dist-tag lags ~3 versions behind the main package; installing without `@next` yields a version whose interfaces don't match the installed main program (the author ate this once: 9 dependency warnings).
- **The doc-vs-code fossil**: the shipped config still carries a comment "remove the disabled marker to use" for the two delegation backends — but the backends were moved out of the installation closure **hours before public release on 2026-08-13**, so following the comment yields a permanently empty slot; two repo docs still claim "the shipped config loads this."
- The deliberate design note quoted: they rejected "ship but dormant" for these packages because dormant parts start no processes yet still cost every production install 245MB of download (为一个默认关着的功能让每个人白下245MB，他们不干).

### 4.10 `~/.agents/skills` read zero-config (§04, §10)

- First-session test 「把你现在能调用的技能全部列出来，一行一个」 listed 57 skills; `ls -d ~/.agents/skills/*/ | wc -l` = 57 (after correcting the author's own `ls | wc -l` = 58 mistake that counted `.git`). The injected catalog is read verbatim — "DeepSeek's product reading things I wrote for Claude Code, as-is, zero config."
- Mechanism: dsh scans six locations, the fifth being the cross-agent public drawer `~/.agents/skills`; names come from the skill file's metadata field, not the folder name (`huashu-weread` listed as `huashu-wereadadvisor`). The book deflates the compatibility halo: dsh didn't build a Claude Code compatibility layer — 它只是恰好翻同一个抽屉 ("it just happens to open the same drawer").
- Three traps: one level deep only (nested dirs deliberately excluded — unlike another agent the author uses, which scans garbage); a one-character typo in the leading name field silently voids the whole skill (camelCase alias acceptance was rejected — see §5); and `~/.claude/skills` is NOT in the scan list (the author survived only because theirs is already a symlink to the public drawer).
- Rule-file behavior verified with a canary experiment (three rule files, each with a secret marker, model asked to recite its sources): `AGENTS.md` and `CLAUDE.md` are both read; byte-identical duplicates deduplicate; drifted content costs double tokens; `.claude/rules/` and `@path` imports are unsupported and pass through as plain text; no file watcher (edits apply on next read/compaction).
- Catalog discipline worth copying: the model sees only name+description (truncated at 500 chars); bodies require an explicit skill call; and stuffing skill bodies into the system prompt was rejected at design time for "destroying progressive disclosure and charging every request for instructions that may go unused."
- First-party write-through: dsh's own write/edit tools invalidate the skill directory when writing skill-affecting paths — a model-created skill is listable in the same step, no watcher latency.

### 4.11 Long unattended work (§09)

- Delegation is five first-class tools (`subagent`, `subagent_fork`, `list_agents`, `send_message`, `interrupt_agent`) — 5 of the 25 standard tools — not prompt folklore. The subagent tool description itself teaches the model epistemic hygiene: the child shares your workspace but not your conversation/tool outputs/reasoning, so 「你把活干完了」本身并不是一个结果 ("'I finished' is not itself a result").
- Plan mode deliberately blocks nothing (soft guidance only; hiding tools would change the prompt prefix and kill the warm cache — one rule sentence instead of a full recompute).
- Goal states (进行中/暂停/卡住/完成) with a strict stuck definition aimed straight at the model's favorite excuse: stuck requires **the same blocking condition persisting three consecutive rounds**, and difficulty/uncertainty/remaining-work explicitly do not count; a mechanical gate rejects stuck claims before round 3, while dsh's own doc downgrades the gate to "a mechanical floor, not an evaluator of same-ness." And the safety rule the book singles out for any checklist: reopening a session never auto-resumes a goal — activation is deliberately not persisted.
- Six subagent backends behind one interface, including "a delegated turn in another product" (Codex / Claude Code via the locally installed, logged-in product; only the turn is borrowed, the whole process tree killed afterward, peer session ids never recorded, peer login/model/settings untouched — no second authority created).
- **The Ralph loop** (fresh worker each round, fixed prompt, state passed only via the shared workspace plus a length-capped handoff note; homage to Geoffrey Huntley's July-2025 technique — the book notes the repo never mentions his name): the anti-context-pollution thesis (early failures, dead ends, and the model's self-narrative all accumulate in a long conversation; round-47's worker sees files, not stories). Handoff reports have exactly three allowed conclusions (continue → must give a next step; done → must show evidence and leave no step; stuck → must name the specific blocker); overlong reports fail rather than truncate; factory cap 64 rounds (package default 256 — don't confuse them). The loop's own documented limit, quoted with approval: completion is a worker's self-claim, not independent evaluation — reviewers, review-driven continuation, completion certificates, adversarial verifiers all deliberately deferred; UI copy is required to say "a worker reported this," never "certified complete." The book marks this section as entirely source/doc-derived (not run).

### 4.12 Code archaeology (§13) and postmortems (§12)

## 5. "They wanted to do X, then didn't" — the rejected-design column, every concrete example

The book's recurring column mines the 11 rejected notes (`.agents/notes/rejected/{simplification,feature}/` — exact file list verified). Each example below with the lesson the book draws:

1. **Soft-blockade sandbox prompt** (§02; shipped then removed on live evidence): stating "bash runs under a read-only sandbox" in the system prompt made the model refuse to even try escalatable work — first live session had 5 of 12 rounds ending with zero tool calls. Named 软性封锁; verdict "shipped first, then removed based on online evidence." Principle: 不要在开头劝退，要在撞墙时给梯子 ("don't discourage at the start; hand a ladder at the wall") — restriction should be felt at the moment of violation, not spread across every breath. Current form: no sandbox wording in the 4,100-char prompt at all; policy arrives as a runtime-context snapshot, and the read-only wording explicitly instructs: "Do not refuse a required modification from this policy alone: try an available tool normally and follow any denial and escalation guidance."
2. **Credential-file read-protection** (§02; written, shipped, withdrawn): a sandbox "this path is unreadable" rule failed on two platform facts (Linux needs a mountpoint in an already-read-only tree → rejects the whole constraint on any machine without saved credentials; the other path can't subtract from already-granted reads → reports "partially held" for a file it never truly hid). Verdict quoted verbatim: 一个在它生效的地方破坏约束、在它不生效的地方谎报状态的保护，比一个被文档化的缺席更糟 ("a protection that breaks constraints where it applies and lies about state where it doesn't is worse than a documented absence"). Replaced with honest docs: stored credentials have **no** boundary against the model (0600 only stops other system users); the real answer (a system keyring the model process cannot read) is a TODO. A second same-note rejection: removing the credentials-dir path from the model's env was rejected as 有真实代价的表演 ("performance with real costs") — hiding the pointer makes the absence harder to see.
3. **landstrip as the Windows sandbox rung** (§02; `.agents/notes/rejected/feature/2026-07-26-evaluate-landstrip-for-windows-sandbox-rung.md`): a days-old single-maintainer ~48-star Rust library covering all three OS sandboxes was rejected with: a dependency carrying a security invariant must have proven adoption — and even swapping the Linux rung to it was separately refused (the current launcher has auditable C source with binaries byte-pinned to their own build, and had just migrated OFF a Rust dependency for that reason). Same day's opposite rule: use mature dependencies rather than hand-rolling — two rules drawing the same line from both sides.
4. **camelCase skill-name aliases** (§04; `2026-07-28-skill-invocation-policy` note's rejected section): reject mercy-aliasing for typo'd name fields — the external format is Claude's hyphenated convention, and a pre-1.0 product owes no compatibility. Team-values exposure: prefer a silently-voided skill over a "guess what you meant" layer; migration advice: spend five minutes scanning name fields.
5. **Drop raw assistant chunks from the log** (§05; `2026-06-20-assembled-assistant-messages-only.md`): store only assembled messages to save log bytes (envelope bigger than content). Rejected for two halves: failed streams live only in chunks (an output-cap round may have no complete message, yet the chunks carry the bill), and keyless replay is built on them. Unless a lossless replacement exists, nothing gets deleted — they compressed the storage format instead (packed rows ≥3).
6. **Compaction-summary cache-reuse alternatives** (§06; `2026-07-21-compaction-summary-prefix-cache-reuse` note's rejected section): the default summarizer broke the just-warmed prefix cache at the conversation's longest point. Three frugal instincts all rejected: keep the summarizer's own system prompt, reuse the rest (the system prompt is the vendor's first-cached segment; change the head and nothing after matters); send only the masked history without the head (divergence from the first token); drop the tool manuals since the summarizer calls no tools (the manuals are part of the cached sequence; dropping them misaligns every following token). Counterintuitive rule: carry the ~20k-char tool manual verbatim even for a tool-less summarizer — sending less costs more.
7. **No-modes, PTC-only fundamentalism** (§08; the Code-mode founding note's first rejection, referencing the Cloudflare original): rejected because the most common coding actions (run a command, read a file, tweak a line) suit native calls — forcing every edit through a program taxes the common case. Reveals a repeated taste: keep four highly-redundant manifest files rather than one clever-but-opaque entrance.
8. **Per-operation tool cards in PTC UI** (§08): rejected because intermediate values are deliberately execution-local and never model-facing; flattening them into cards would expose an implementation trace instead of the one operation you and the model actually initiated.
9. **A default plugin to fix the PTC direct-call bypass** (§08): rejected in one sentence — a security invariant must never depend on the deployer having composed the right plugin (hence the executor-level block of #4.5).
10. **Self-check via the settings-page "is-broken" field in Creator mode** (§07): rejected because it admits every fatal failure class while presenting itself as validation — 看起来完整，是它最危险的地方 ("looking complete is its most dangerous property").
11. **Collapse workflow to foreground core** (§09; `2026-07-12-collapse-workflow-to-foreground-core.md`): diagnosis fully conceded (a whole progress-observation system with zero production listeners) but the prescription rejected — the observability interface is deliberately designed; find it a consumer, don't delete it. The book calls this the subtlest of the 11: diagnosis accepted, prescription refused, conclusion "redesign the relevance contract" — which is why no workflow progress bar exists in the UI today.
12. **Prune the unused skill-registry API** (§10; `2026-07-12-prune-unused-skill-registry-api.md`): no internal caller exists; rejected because runtime skill registration is a deliberately reserved third-party extension path — 没有内部调用者不等于没用，它是留给外人的门 ("no internal caller ≠ useless; it's a door left for outsiders").
13. **Fold the compaction definition into its only implementation** (§11; `2026-07-19-fold-compaction-package-split.md`): the proposal quoted the three-roles design note against itself; rejected in one line — more compaction backends are on the roadmap. The book: a rule was used to oppose its own existing implementation and was stopped by the roadmap.
14. **Keep the .dsh-plugin special format / migration parser** (§10; `.agents/notes/implemented/simplification/2026-08-09-remove-repository-plugin.md` — a deletion note, but its rejected section preserves the alternatives): skills and MCP need no special channel; they are ordinary plugins; even a migration parser was refused (keeping a deleted convention alive); old packages simply stop working, no migration, no cleanup.
15. **The in-web YAML config editor** (§11): built, then deleted; new modes only by copy-and-edit. Two hard sentences: "humans don't write YAML from zero" (a blank editor is freedom nobody uses), and "weak as an editor, wide as a capability" — no completion/highlighting, yet it accepts executable expressions, i.e. arbitrary code on next mount. Worst combination: can't help you write correctly, can let you write wrong very far. The deletion forced a new mechanism (mtime/size generationing of the mount layer).
16. **Keep the terminal UI (three softer options)** (§11): after ~40 design notes (14 in one day) and weeks of polish, the full-screen terminal UI was deleted wholesale on 2026-08-04 (source, tests, snapshots, deps, docs); "keep unpublished" (an unsupported thing still reads as a reusable surface), "move to examples" (moving code provides no requirement/maintenance/acceptance), "compat shim" (config rows depending on it just fail) all rejected. Same judgment: a thing with no consumer, maintainer, or acceptance is debt in any directory — merely better disguised. The terminal UI now lives outside as turtle-ui (referenced in `.agents/notes/implemented/architecture/2026-08-06-app-owned-command-line.md`; the book notes the external repo was unreachable at publication time, and that turtle-ui later added two CLI flags with zero launcher changes — dsh reading it as design validation). The book's framing: the terminal UI is most coding agents' entire face; building it for two weeks then deleting it clean is everything-is-a-plugin's most expensive self-proof.
17. **Truncate interrupted turns instead of synthesizing results** (§12; `2026-06-20-truncate-interrupted-turns.md`): drop everything after the last complete turn on crash recovery; rejected because a turn can carry large real work — discarding it costs more than one dirty record (this is the crash-honesty text of §4.12).
18. **A notes index page** (§13): classification checks reject a root index file; deleted 2026-07-19 because with agents committing in parallel, a generated index is a predictable merge-conflict hotspot. Book: this judgment only holds under agent-scale parallelism — humans-at-3-commits-a-day should keep their index.
19. **Assembled-messages-only + fold-session-persistence-interface** (§13/§14; `2026-06-20-fold-session-persistence-interface.md`): folding the storage-interface package back into the main package, with the honest self-diagnosis that a lone interface with no third-party implementer looks like premature abstraction; refused with the roadmap line — if third-party storage backends became a public ecosystem, the split IS the cleaner boundary. The book: they admit it's a bet, then bet. 2026-06-20 was a five-rejection day (assembled-messages-only, drop-bash-output-spill-files, drop-durable-step-boundaries, fold-session-persistence-interface, truncate-interrupted-turns — all five preserving the log's completeness).
20. **The beta-declaration first-screen popup** (§01): deleted on publication day per a note ("internal-testing positioning shouldn't appear in a release"), the telemetry-paragraph-only compromise also rejected (a content-free forced first screen is pure friction) — then half-restored the same day. The popup you see is the residue of that day's round-trip.
21. **Auto-judging non-triviality for the notes rule** (§13): the one human-only gate, §4.12.
22. **YAML config editor blank-new** and **`No runtime invariant` placeholder tolerance** are covered in 15 and §4.12 respectively.

## 7. The author's verdict (§14): four bets and their prices

1. **Bet: everything-is-a-plugin → ecosystem. Price: out-of-box experience.** Even the main loop is a `disabled: true` row; the strongest self-proof is what they deleted (.dsh-plugin format, YAML editor, the terminal UI). The price is stated by insider JY (quoted twice): current experience is genuinely less polished than Claude Code/Codex; interfaces changing; plugin ecosystem just starting. Concrete measured gap: 133 plugins running, 3 configurable in the UI.
2. **Bet: every run leaves a trace → auditability. Price: disk and simplicity.** Append-only event stream, 3/44 model-visible; the PTC no-shared-state decision trades performance for the every-request-is-a-pure-function-of-the-log invariant (opposite direction from Anthropic's code-execution state persistence); an echo task = 35 physical records; no retention policy by decision; nothing is ever surgically erasable.
3. **Bet: skills/MCP as ordinary plugins → abstraction correctness. Price: fit.** Net win for the author (the widest skill door in the industry — 57 skills read with zero config); net loss for heavy MCP users (only the tools verb bridged, zero servers mounted by default, each server command is "trusted executable code outside the agent sandbox"), plus the 35 out-of-tree packages with the @next trap.
4. **Bet: the model company ships its own harness → capability realization. Price: neutrality.** Anchored by the Composio experiment (fixed model, 8 harnesses, 240 runs: 46.7%–66.7% pass, ~7x cost-per-success spread; 7 tasks decided purely by harness choice); minimal mode exists to benchmark the model with the scaffolding stripped (four deliberate strippings, including refusing full-access because the tool schema would still show `sandbox_permissions`/justification fields — they removed the restriction's *visibility*, not just the restriction); the un-removable anonymous UUID is the neutrality price, disclosed by dsh in its own gated "Known Limitations" sections (220 files measured).

Who it's for / not for (book's own triage): for people who want to understand how agents work under the hood (the only fully-open implementation with 600+ design notes), plugin/tool/UI builders (earliest ecosystem position), and skill-asset owners wanting a second harness without moving house; not for Python-stack embedders (TS ecosystem, no HTTP bridge layer), multi-tenant/concurrent/billing deployments (absent), or anyone wanting a smoother coding assistant without tinkering. The author's personal position: not switching from their main tools (stability over disassembly); two uses — a second touchstone for the skill ecosystem ("a skill set is only truly alive if it runs on two harnesses"), and source material, because dsh is the first product to lay out "what does the model actually see" completely. Closing beat: the Hacker News exchange — asked "who did they copy this time?", the reply: "because this time it looks pretty much original?" — a company long accused of copying first credited with originality, not for a model, but for open-sourcing a harness.
