## 3. W1 — Usage governance (finish half-done work)

### 3.1 Current state (already on disk, uncommitted)
- `src/types.ts`: `AgentUsage`, `SpawnResult.usage`, `RunUsage`, `RunSummary.usage`,
  `StageContext.usage` (accumulator) — done.
- `src/agents/delegation-backend.ts`: parses `resp.usage` (already did for the
  terminal log line) and now threads it onto the returned SpawnResult — done.
- `src/workflow.ts`: accumulator creation + per-call merge helpers — partially
  in (3 known TS errors to resolve).

### 3.2 Design
Data flow:
```
child (pi-subagents) → resp.usage {input,output,cacheRead,cacheWrite,cost,turns,toolCalls,durationMs}
  → SpawnResult.usage (typed, optional; absent = absent — P10, never zeroed)
  → workflow exec closure: fuse check BEFORE dispatch → accumulate AFTER response
  → ctx.usage (UsageAccumulator: adds + counts calls / callsWithUsage)
  → RunSummary.usage + audit row + run-metrics.jsonl (W2)
```
- **Fuse inputs**: `SUPER_DEV_MAX_RUN_COST` (USD float) and `SUPER_DEV_MAX_RUN_TOKENS`
  (int, counts input+output). Optional `runBudget:{maxCostUsd,maxTokens}` in
  ~/.super-dev/config.json — env wins over config (matches SUPER_DEV_THINKING precedent).
- **Fuse check** happens before dispatching each agent call:
  - `usage.costUsd > maxCost` or `usage.tokens > maxTokens` → do NOT dispatch.
- **Fuse trip behavior (recommended option A)**: return a per-call error
  `run budget exceeded: cost $X.XX / limit $Y.YY (tokens N / limit M)` marked with a
  distinct class (`isBudgetExceededError`), set `ctx.fuseTripped = "cost" | "tokens"`,
  log one WARN with remedy (raise env/config or resume later), audit row
  `pipeline.budget` status=failed reason=budget-exceeded.
- **Deterministic wind-down**: extend the F9-C pattern — `shouldIterateImplementation`
  / `shouldRunVerification` (and the docs/merge gating that already keys on
  hasVerifiedImplementation) also stop when the fuse marker is set; remaining
  deterministic stages (summary, completion audit, metrics write) still run.
  Zero further agent spend; state is coherent; resume with a raised limit continues
  (partial-preserve machinery unchanged).
- **In-flight call**: never killed — its tokens are already spent; killing wastes
  the partial work and leaves messier state. (This is the essential difference
  from hard-abort; see §6.1.)
- **Telemetry-absent owners** (older pi-subagents without usage in responses):
  fuse cannot evaluate → log once "usage telemetry unavailable — budget fuse
  inactive (P10)" and proceed. Fail-open-harmless (P4): the fuse is protection,
  not a correctness gate. `callsWithUsage/calls` ratio in metrics makes the
  blind spot visible.

## 4.1 F10-3 closed — first-principles effort statement (D2)

Effort is not a static label→cap table; it is bounded by evidence, dynamically:
- F2 strict-progress: convergence budget auto-extends only when fresh reading
  progress occurs (no progress → no extension).
- Oscillation detection (3-try no-progress stop), stall detection, round caps as
  the outer bound.
- F9-C replan wind-down: superseded plans stop consuming effort.
- W1 budget fuses (this version): effort also bounded by absolute cost.
A per-taskType table would be a weaker static proxy for exactly this machinery,
and would mislabel edge cases (big bugs, tiny features). Documented in the
findings file as closed-by-design.

## 5. W3 — Structured delegation (F10-6, promoted per D4)

### 5.1 Verified facts (pi-subagents 0.65 source)
- `SubagentDelegationResultRequest = {kind:"text"} | {kind:"structured", schema}`
  (api/delegation.ts:21-22) — the schema is a plain JSON-Schema object
  (`Record<string, unknown>`); TypeBox `Type.Object(...)` values ARE such objects.
- Structured path: child is injected a `structured_output` tool + the schema;
  the child MUST finish by calling it (`MISSING_STRUCTURED_OUTPUT_CALL_ERROR`
  otherwise); the value is validated against the schema at completion
  (`validateStructuredOutputValue`); response arrives as
  `{kind:"structured", value}`; dedicated statuses `structured_output_failed`,
  `acceptance_failed`.
- Our side: every writer/reviewer/classifier call already carries
  `schema: STAGE_MODELS[…].schema` (TypeBox, importable via `typebox` provided by
  the pi runtime — zero-dep property preserved). The only dead link is
  delegation-backend always sending `result:{kind:"text"}` and re-parsing prose.

### 5.2 Design
1. **Request wiring**: in delegation-backend, when `call.schema` is present →
   `result: {kind:"structured", schema: structuredClone(call.schema)}`;
   otherwise keep `{kind:"text"}` (prose-only calls: classifier-free helpers,
   orchestrator chat, reflection).
2. **Response handling**: `value.kind === "structured"` → candidate control is
   `value.value` (object) → still funneled through engine-side validation
   (extractControl/missingControlKeys → now schema-aware, see 3) — P5: our gates
   stay authoritative; upstream validation is a filter, not the oracle.
3. **Engine-side schema validation + repair feedback**: validate the control
   against the same schema with TypeBox `Value.Check/Value.Errors`
   (`import { Value } from "typebox/value"` — same resolution context as
   `import { Type } from "typebox"` in extension.ts; **spike first**, fallback =
   small in-engine validator for our schema subset: required keys, primitives,
   string-array, enum). On violation: corrective re-prompt (existing loop) now
   carries the DETAILED errors (`/control/verdict: expected union…` paths from
   Value.Errors) instead of only missing-key names — industry validate→repair
   pattern (LangChain docs: "agent provides specific error feedback"; n8n 2026:
   validate keys/types/enums → repair once with the error → bounded retries).
   Bounded as today (corrective rounds cap).
4. **Compat — owners without structured support (e.g. in-memory 0.64 skew)**:
   on `invalid_request` matching structured/schema fields → sticky per-process
   degrade to text mode for schema calls (class-level, mirrors the
   version-skew degrade), honest WARN once, prompt-embedded schema (current
   behavior) remains the fallback path. Never fatal; P4 fail-open-harmless.
5. **STAGE_MODELS audit**: ensure schemas are plain-data TypeBox (no functions),
   `$schema` key present is fine; list any stages whose schema is missing while
   controlKeys exist → add schemas opportunistically where cheap, do not block.

### 5.3 Tests (new tests/structured-delegation.test.ts)
1. schema-carrying call → request body has `result.kind==="structured"` and the
   schema object (deep-equal); text calls unchanged.
2. structured response `{kind:"structured", value:{…}}` → control accepted when
   schema-valid; extractControl still applied.
3. schema-invalid value (wrong type on a field) → corrective re-prompt contains
   the Value.Errors path text; second (valid) response converges; no more than
   the bounded rounds.
4. missing structured_output → child error surfaces honestly (status
   structured_output_failed named in reason), bounded retry, no canned lie (P10 —
   same honesty rule as F9-B).
5. owner returns invalid_request (structured unsupported) → sticky degrade:
   subsequent schema calls go out as kind:"text", one WARN, run continues.
6. Spike test: `typebox/value` import resolves (or fallback validator chosen) —
   decides implementation path 3 early.
7. E2E smoke (real owner, scratch env pattern from v0.4.0): one real delegated
   call with schema returns a validated structured value.

## 5.4 W4 — Review policy caps (F10-4)

`agents/code-reviewer.md` + `agents/adversarial-reviewer.md` (+ tests-review
prompt guidance inside code-reviewer) gain:
- **Important vs Nit definitions**: Important = correctness, security, data loss,
  performance, contract breaks, test gaps on changed behavior. Nit = style,
  naming, preference, non-idiomatic-but-correct.
- **Nit cap**: at most 3 nits total; when any blocking (Important) finding
  exists, report only blocking findings.
- **Do-not-report list**: formatting/lint-covered issues, hypotheticals without
  evidence, adding tests for unchanged behavior, TODO suggestions unless
  risk-related, restating what the code does.
- **Output discipline**: file:line + severity + one-line fix; no code restatement.
Token rationale: review outputs feed writer re-prompt rounds — shorter, higher-
signal findings shrink every downstream round (OpenAI guidance: "concise,
high-signal; verbose responses get ignored"; SDLC REVIEW.md play: "cap the nits").

## 6. Open decisions for the user

### 6.1 Fuse semantics (D1) — 两种方案的区别

**方案 A — per-call fail-closed + 有序收尾（推荐）**
每次 agent 调用**派发前**检查累计 cost/tokens；超限后，下一次调用直接返回
"run budget exceeded" 错误——不派发、不花 token。正在飞行中的那一次调用让它自然
跑完（钱已经花了，杀掉只会浪费已完成的部分并留下脏状态）。剩余的确定性步骤
（build gate 结论、RunSummary、completion audit、metrics 落盘）继续走完，运行以
`budget-exceeded` 状态**完整收尾**；提高上限后 resume 可继续（partial-preserve
机制不变）。

**方案 B — hard abort（立即硬中止）**
超限瞬间抛 FatalAbort，整个 workflow 当场停止，任何收尾都不做。

**本质区别**：A 的止损点是"下一次花钱的地方"，B 的止损点是"此刻"。熔断触发后
A 的收尾阶段已经没有任何 token 支出（只剩本地毫秒级确定性步骤），所以 B 唯一
能"更快"的地方恰恰是没有价值的地方，却付出了收尾不完整、审计断档、状态更脏
的代价。**A 严格占优，推荐 A。**

### 6.3 结构化委派详解（回答"我们的 schema 是需要改进吗"）— D7 背景

**结论先行：我们的 schema 本身不需要改进。** 每个 stage 调用早已携带 TypeBox
构建的 typed JSON Schema（STAGE_MODELS，extension.ts `import {Type} from 'typebox'`，
零运行时依赖不破）。断的不是 schema 质量，而是**传递链路**：
`delegation-backend.ts` 硬编码 `result:{kind:"text"}`，schema 在 workflow.ts 组装
common object 后就断头——子代理从未见过 schema，只能写散文，引擎再从散文里抳
control 对象。

**现状（text 模式）的验证链只有一层半**：
1. 子代理写散文（无任何结构约束）→
2. 引擎正则/JSON 提取 →
3. 只有 `missingControlKeys`（缺 key）检查；**字段类型错了不检查**
   （如 severity 传了 `"critical!!"`，只要 key 在就放行）→
4. 纠错 prompt 只说“缺什么 key”，不说“哪里类型错”→
   一轮 agent 调用（≈几十秒 + token）浪费在盲猜上。

**结构化模式（pi-subagents 0.65 原生支持，无需上游改动）加三层防线**：
1. **生成时约束**（pi ≥0.82 constrained tool sampling，capability-gated）：
   schema 传到子代理的 `structured_output` 工具后，支持的 provider 会在 token
   层面强制 strict JSON —— 结构违规在生成时就几乎不可能发生；
2. **完成时验证**：子代理必须调用 `structured_output` 才算完成；值在完成时用
   schema 验证（`validateStructuredOutputValue`），从不调用 →
   `structured_output_failed` + MISSING_STRUCTURED_OUTPUT_CALL_ERROR；
3. **引擎侧纠错反馈升级**（W3 自己的代码）：TypeBox `Value.Errors` 把具体错误
   （"/findings/0/severity: expected union"）回传给子代理纠错——从“缺 key”
   升级为“精确路径+原因”，纠错轮次预期下降。

**兼容性（粘性降级的含义）**：0.64 的 owner 不认识 `kind:"structured"`，会返回
invalid_request。首次命中后进程内记住（sticky），后续全部自动退回 `kind:"text"`，
代价仅首次一达失败调用的重试（同 version-skew 降级同类，已验证过这个类）。

**风险（为什么不是无脑默认开启）**：结构化模式改变子代理的**完成契约**——
它必须以工具调用收尾。glm 系列对“严格 JSON 工具调用”的服从度未经我们验证，
可能出现 structured_output_failed 高发、收敛轮次变多的行为级回归；且我们全部
3184 个测试都在 text 路径上，结构化路径目前零 E2E 证据。

**两个选项**：
- **A. 默认开启**：带 schema 的调用直接发 structured。收益：立即生效；风险：上述行为级变更无证据就进生产。
- **B. `SUPER_DEV_STRUCTURED=1` 试用一版**（推荐）：接线全部完成，但默认关；用一个版本周期跑真实运行收集证据（结构化失败率、纠错轮次、成本变化），v0.3.70（W3 版本）再翻默认。符合 Arize "prove each update" 与我们 P 系列"证据先行"。

### 6.3.1 深化研究后的修正结论（2026-09-05，用户追问后）

**本地新事实（比先前风险估计更重要）**：0.65 的 `structured_output` 工具在
**调用时即时验证**（subagent-prompt-runtime.ts:420——子代理提交非法值，工具当场
拋 `Structured output validation failed: <message>`，子代理在自己会话内看到错误
**当场重试**，不烧一整轮委派）；成功即 `terminate:true` 收尾。即：结构化失败
的大多数情形被限制在子会话内部，代价只是子代理多几个工具调用轮，而非
新一轮 30-60s 的委派重试。

**在线研究结论（AnySearch，4 组查询）**：
- **行业默认已收敛为"传 schema 即强制"**：OpenAI Structured Outputs 2026 年
  strict mode 已是默认；Anthropic/Google 2026 在采样层强制 JSON Schema；
  LangChain `with_structured_output`/PydanticAI/Vercel AI SDK `output` 均
  "schema 即强制"，没有一家把 schema 传递做成需要额外开关的 opt-in。
- **特性开关最佳实践**（ConfigCat/DraftKings/Unleash/GitLab）：默认关适用于
  *面向用户、行为未知*的新功能；而"默认开 + 安全回退 + 稳定后**移除**开关"
  是已验证行为的成熟路径；遗留开关本身是技术债（N 套代码路径都要验证）。
- **B 方案的致命缺陷（用户指出）**：`SUPER_DEV_STRUCTURED=1` opt-in 依赖人记得
  设置——忘了设 → 接线永远休眠 → "收集证据"计划静默失败，等于没实现。

**修正提议：方案 C —— 默认最佳 + 分层自动回退 + 短命逃生门**：
1. **默认 = 最佳**：带 schema 的调用直接发 `kind:"structured"`（行业对齐）；
2. **回退层 1（自动）**：owner 不支持（invalid_request）→ 首次命中后 sticky 降级
   全进程 text 模式（同 version-skew 类，已有成熟模式）；
3. **回退层 2（自动）**：连续 N 次 `structured_output_failed`（模型确不能服从）
   → sticky 降级 text + honest log（防 glm 服从度问题的有界爆竹半径）；
4. **逃生门（人可拉）**：`SUPER_DEV_STRUCTURED=0` 强制关（语义反转：从 opt-in 变
   opt-out，最佳已是默认，忘不忘记都无损）；
5. **开关生命周期**：v0.3.70 引入，稳定两个版本后移除（ConfigCat/DraftKings
   实践），避免开关债。

**证据补强**：W3 的 E2E 验证（§5.3.7）在真实 glm 子代理上跑结构化路径，
结构化失败率/纠错轮次写入 W2 的 run-metrics（structuredFailures、
callsStructured）—— "prove each update" 由数据落地，而非靠人工开关。

## 9. W5 — Auto-continuous evolution loop (standalone v0.3.69 per D9; E1 depends on W2)

User question (2026-09-05): "how does our continuous evolving work? is it the best pattern? what
aspects make a more auto-continuous-evolving harness?" Research corpus: Lilian Weng
"Harness Engineering for Self-Improvement" (2026-07), Self-Harness (arXiv 2606.09498),
Agentic Harness Engineering / AHE (arXiv 2604.25850), Arize "prove each update",
PyMC Labs "when skill optimization works", Voyager skill-library line.

### 9.1 Current loop — honest map

| Best-pattern element | Our state | Verdict |
|---|---|---|
| Component observability (every editable harness component is a file; failure→component mapping) | agents/*.md, methodology/*.md, src/*.ts, config — all files; F1–F9 each name file:line | ✅ already best-in-class |
| Experience observability (agent-debugger: trajectories→per-task root-cause reports→aggregated overview, layered access) | run.log/events.jsonl exist per run, but analysis is MANUAL (a human+agent session reads logs on demand) | ❌ gap → E2 |
| Deterministic failure clustering (verifier-cause × behavior × mechanism signature) | escape-class taxonomy P1–P10 exists, but incident→class assignment is manual, no signature matching | ◐ gap → E2/E5 |
| Decision observability (every edit = falsifiable prediction validated next round) | every fix ships class-level RED-first tests, but no run-level metric check that the fix worked in production | ◐ gap → E5 |
| Evidence-gated promotion + anti-reward-hacking | TDD + full suite + coverage hard gates + E2E for risky classes; gates non-disablable (P5); tool allowlists | ✅ |
| Governance by risk tier + rollback (Arize: memory/prompt → policy → code, each with minimum evidence; autonomy ∝ reversibility×blast-radius) | human owns every fix (approve→TDD→commit→version); git rollback | ✅ |
| Continuous evals (benchmark re-runs on every model/prompt change) | incident-derived behavioral tests exist but unlabeled, no eval runner, no model-change gate | ❌ gap → E4 |
| Telemetry → drift detection (σ-bands) | none — failures noticed only when the user reads logs | ❌ gap → E1 (W2 metrics is the enabler) |
| Skill accumulation (Voyager-style) | harness's own incident runbooks live in methodology prose only, not agent-callable | ◐ later → E6 |

Conclusion: our FIX lifecycle discipline (findings→class tests→version) is already the
governed half of the best pattern; what's missing is the AUTOMATIC half — measure,
detect, diagnose, cluster, verify-predictions. That is exactly the 2026 literature's
"self-harness" loop, and it composes with our governance instead of bypassing it.

### 9.2 The seven aspects (what makes a harness auto-continuous-evolving)

1. **Measure** — machine-readable per-run telemetry (W2, v0.3.68).
2. **Detect** — statistical drift detection over metric baselines (E1).
3. **Diagnose** — fresh-context post-mortem agent over run artifacts, layered/progressive disclosure (E2; Weng's Agent Debugger).
4. **Cluster** — match new failures to prior escape classes by deterministic signature, not semantics (E2/E5; Self-Harness clustering).
5. **Decide** — human triage of drafted findings, risk-tiered promotion evidence (E3; Arize).
6. **Learn** — validated persistent updates (already our fix lifecycle) + distillable skills (E6, later).
7. **Prove** — falsifiable per-fix predictions verified against post-fix metrics; eval suite re-run on model/config changes; named rollback (E4/E5).

### 9.3 Work items (v0.3.69)

- **E1 σ-band monitor** (deterministic, zero-LLM): post-run step + `super-dev triage`
  command reads run-metrics.jsonl rows across runs; trailing baseline median+MAD per
  metric (agentErrorRounds, retries, gateBlocks, costUsd, durationMs, rounds/stage);
  1σ → log; 2σ → auto-run E2 on that run; 3σ → also draft intent + surface. Bounds:
  needs ≥ N (e.g. 8) prior runs before banding; no LLM anywhere in detection.
- **E2 Post-mortem agent** (Agent Debugger): new read-only sd-post-mortem role;
  invoked automatically at run end when status=failed/degraded (config flag
  `postMortem: "auto"|"manual"`, default manual-first for safety) or on demand.
  Input = metrics row + run.log/events.jsonl PATHS (JIT reading, truncation canon) +
  findings-ledger index for class matching. Output = finding draft in
  `docs/findings/inbox/` with: evidence quotes (file:line), root-cause hypothesis,
  escape-class match, proposed class-level fix + pinning test, falsifiable prediction.
  NEVER edits methodology/src/prompts directly (advisory only; human Owns).
- **E3 Triage command**: lists inbox findings, approves → intent/task file (existing
  fix lifecycle takes over). The Decide gate stays human.
- **E4 Eval harness**: `npm run evals` runs labeled behavioral suites (rename/tag the
  incident describes already in tests/); document the model-change gate (agentModels/
  agentThinking edits should pass evals before trusting a long run). CI wiring later.
- **E5 Prediction ledger**: each finding gains a `prediction:` field (metric +
  expected direction); E1 marks verified/refuted after enough post-fix runs; findings
  ledger gains a status column. Closes decision observability.
- **E6 Harness skill library** (optional, later): distill recurring incident runbooks
  into agent-inheritable skills (composes with D3 uniform skills-ON).

Governance guardrails (Arize tiers, non-negotiable): drafts land in inbox only;
persistent changes always go through human-approved fix lifecycle + tests; code-tier
changes need full suite + E2E; rollback = git revert; post-mortem agent is read-only
+ inbox-writer; no agent may edit gates, methodology, or evals.

### 9.4 Explicitly NOT adopted from the literature

- DGM/AlphaEvolve-style autonomous self-modification of harness source (no human gate)
  — violates our Own boundary and Arize's code-tier evidence bar.
- Semantic (embedding) trace clustering — Self-Harness shows deterministic
  verifier-grounded signatures are sufficient and auditable; ours = escape classes.
- Auto-applying prompt edits from post-mortems — promotion is human-tiered.
