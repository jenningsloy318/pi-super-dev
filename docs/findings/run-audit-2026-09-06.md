## M1 — RED-review verdicts discarded on concurrent-writer quarantine [HIGH]

Evidence: 6 quarantines (phases 1,2,3,4,5,9), 54.0 min reviewer time discarded, 3 open
completion findings ("RED review did not complete"), 2 "coverage gate UNMEASURABLE".

Chain: `workflow.ts realAgent` — `enforceSourceBoundary()` runs AFTER
`runWithTransientRetry` returns, so the reviewer's fully-formed control exists in the
try block; the quarantine throw (v0.3.54) discards it. The join
(`implementation.ts` ~2637) fail-opens correctly (GREEN work kept) and
`attributQuarantinedViolations` (:1255) already computes whether every violated path
is claimed by the concurrent implementer — but that signal only drives RESTORES, never
verdict salvage. Quarantine paths in this run were 100% the implementer's declared
files every time (the reviewer demonstrably wrote nothing).

Fix (class): attach `salvagedControl` to the thrown boundary error in realAgent's
catch; extract a pure `attributeQuarantinePaths()` classifier from
`attributQuarantinedViolations`; at the join, when attribution fully clears
(declaredAny ∧ zero unclaimed), accept the salvaged verdict and run normal
strong/weak adjudication with an honest "verdict salvaged (violations fully
attributed to concurrent writer)" log. Not-fully-attributed or no-claims → today's
fail-open.

Dual-review refinement (AR-73-01, 2026-09-06): the evidence line above overclaims —
full attribution establishes "covered by the concurrent writer's declared claims", NOT
"the reviewer demonstrably wrote nothing": phase test files claimed UNCONDITIONALLY
would attribute a reviewer-written test file away. The salvage gate therefore runs the
classifier with `testFilesAsClaims: false` (implementer-DECLARED claims only); a
test-file violation stays unclaimed → no salvage → fail-open keeps the work. The
restore path keeps the unconditional semantics (a test-file delta must never be
git-reverted).

## M2 — tests-review artifact never rendered [HIGH]

Evidence: Stage 10a2 completed 5 times (control=yes) yet no `NN-tests-review.md` exists
in the spec dir; the tests-reviewer's own deferred finding says so.

Root cause: `verify.ts` — codeReview and adversarialReview tasks call `renderAndWrite`,
the testsReview task does not; `STAGE_MODELS` has no `testsReview` entry (renderAndWrite
silently returns null for unknown stages).

Fix: `STAGE_MODELS.testsReview = { slug: "tests-review", schema: CodeReviewData,
template: "code-review.md.njk" }` + `renderAndWrite(...)` in the testsReview task.

## M3 — agent-failed findings never close on later success [HIGH]

Evidence: round-5 code review APPROVED (rendered 18:07) and tests-review completed
(18:08), yet completion audit lists `codeReview-agent-failed` / `testsReview-agent-failed`
as [open·blocking] — 2 of the 9 "deferred" human-decision items are stale phantoms that
poisoned the final decision surface.

Root cause: `convergence-ledger.recordConvergenceFindings` only updates rows it
receives; a later successful verify round (whose control does NOT carry the finding)
never closes the row opened by an earlier round's `failedReviewControl`.

Fix: close-on-success — when a verify round's review control for kind X is a valid
review (not failedReviewControl), mark ledger rows `${kind}-agent-failed` verified with
a closure note naming the round.

## M4 — reviewer timeout tier one notch too tight [HIGH]

Evidence: 7 exact-20:00 delegation timeouts (specReview ×3, verify code-review ×2,
adversarial ×1, tests-review ×1) ≈ 140 min discarded + full re-review cost each.
Completions run 11–19.5 min — the 20-min default has no headroom for review roles on
this model.

Fix: reviewer roles (code-reviewer, adversarial-reviewer, spec-reviewer,
requirements-reviewer, bdd-reviewer, design-reviewer) join the 30-min tier in
`defaultAgentTimeoutMs` (`REVIEW_TIMEOUT_MS = 1_800_000`).

## M5 — σ-band baseline polluted by test-suite rows [HIGH]

Evidence: `~/.super-dev/run-metrics.jsonl` has 481 rows of cost=0/agents=0 test rows
→ medians 0/MAD 0 → every real run fires fake 3σ (wallMs "99σ") on all five bands.

Root cause: 6 test files drive `runWorkflow` to close-out without mocking
`getSuperDevDir` (cleanup-sensitive-scan, runlog-agents, runlog-invariants,
runlog-wiring, team-raci, workflow), so `appendRunMetrics`'s global write lands in the
real user ledger on every suite run.

Fix: `SUPER_DEV_NO_GLOBAL_METRICS=1` guard on the global append (per-specDir write
unaffected — hermetic); set the env in `tests/setup/config-env-hermeticity.ts`; the two
metrics-asserting suites clear it locally; one-time cleanup of the real ledger
(backup + keep rows with agentsSpawned>0 ∨ costUsd>0 ∨ wallMs≥60s).

## M7 — implementer self-commits mid-phase [MED]
