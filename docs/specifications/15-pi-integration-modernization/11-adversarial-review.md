Verdict is CONTEST rather than PASS on two medium-severity quality concerns that warrant an author response: (1) a session-vs-subprocess model-resolution asymmetry where an inherited model id that is not resolvable through a freshly-created, NON-network-refreshed `ModelRuntime` catalog is silently DROPPED on the session backend while the subprocess backend honors it unconditionally — so the headline Feature-1 acceptance ("every spawned specialist on BOTH backends uses that model") can quietly fail on the session backend with zero signal; and (2) an undocumented global render-validation semantics change in `validateData` (silently dropping ALL "must not have additional properties" errors, not just for strict-capable schemas) that broadens beyond the feature's stated scope and is absent from the CHANGELOG's "byte-identical fallback" claims. Neither risks production failure, data loss, or security breach (both degrade no-throw / gracefully), so REJECT is not warranted. Test coverage for the new precedence tiers, `isStrictCapable` gating, and build-correlation is solid and the mocking strategy is sound (vi.hoisted + vi.mock of the SDK and ModelRuntime).

### F-1: Session-backend inherited model is silently dropped if absent from a non-network-refreshed ModelRuntime catalog — diverges from subprocess backend

- **Severity**: medium
- **Lens**: Skeptic
Feature 1's acceptance requires that BOTH backends use the live session's model when no override is supplied. The subprocess backend (`buildSpawnArgs`, src/pi-spawn.ts ~resolveModel/buildSpawnArgs) passes the raw inherited id to `--model` UNCONDITIONALLY and lets pi's CLI resolve it. The session backend (`resolveSessionModel`, src/session-agent.ts) instead resolves the id against `ModelRuntime.create()` and, per the verified 0.82.1 d.ts, that class's `create()` defaults `allowNetworkRefresh` to FALSE — so the catalog it scans is the bundled one, NOT the user's provider-configured catalog. If `ctx.model.id` is a custom-provider / OpenAI-compatible / settings-configured model the bundled catalog doesn't know, `resolveSessionModel` returns undefined and `createAgentSession` omits `model`, falling through to the SDK/settings default. The subprocess backend honors the inherited id; the session backend silently does not — a divergence from 'every specialist on BOTH backends uses that model' with NO observable signal (the no-throw fall-through is intentional and correct for robustness, but masks the divergence). Mitigations: (a) when an inherited id is supplied but fails catalog resolution, emit a one-line best-effort `ctx.log`/progress note so the divergence is observable; or (b) fall back to passing a minimal `{ id }` descriptor to `createAgentSession` (the SDK may still resolve it via settings, which often equals the right model anyway). At minimum, document the asymmetry and the `allowNetworkRefresh=false` assumption in the comment block on `resolveSessionModel`. Tagged UNCERTAIN on real-world blast radius because the settings-default fall-through frequently coincides with the correct model.
### F-2: validateData now silently drops ALL additional-properties errors globally — undocumented render-validation semantics change

- **Severity**: medium
- **Lens**: Skeptic
src/render/render.ts `validateData` adds `if (e.message === "must not have additional properties") continue;` for EVERY schema, gated only by a comment, not by `isStrictCapable`. This was necessitated by closing the review/implementation schemas (additionalProperties:false) in src/render/schemas.ts so strict constrained-sampling works, but it removes a general render-validation guarantee: any FUTURE or OTHER schema that intentionally sets `additionalProperties: false` to ENFORCE no-extra-keys at render time will silently stop enforcing it, and a model emitting junk keys into such a schema will render instead of failing its gate. The CHANGELOG's Feature-2 bullet claims the non-capable/permissive path is 'PRESERVED byte-identical' — that is true for the structured_output/missingKeys path, but render validation semantics changed globally and that change is not mentioned. Recommend: scope the tolerance to strict-capable schemas (skip the error only when `isStrictCapable(schema)` is true, OR only for schemas explicitly marked as the constrained-sampling variant), and add a line to the CHANGELOG noting the deliberate global change. If the intent really is global, make that explicit in the comment rather than framing it as a strict-capable-only accommodation.
### F-3: Session backend couples to a fresh ModelRuntime catalog subsystem, duplicating resolution logic the SDK/settings layer already owns

- **Severity**: low
- **Lens**: Architect
To thread `model?: Model<any>`, Feature 1 introduces `getModelRuntime`, `splitModelRef`, `resolveSessionModel`, and a process-wide `runtimeCache` (src/session-agent.ts) that reach into pi's `ModelRuntime` catalog and do provider-splitting + full-catalog scans. The spec envisioned 'pass the resolved model via the SDK's model option'; this implementation owns model resolution end-to-end instead. It is correct and no-throw, but it is a meaningfully larger surface than required and must track pi's catalog/resolution evolution. If `createAgentSession` ever accepts a bare id (or resolves a `{id}` descriptor via settings — which is what its own default path does), most of this subsystem collapses. Consider whether a minimal descriptor + settings fall-through would reduce coupling; if keeping the catalog approach, isolate the resolution so a single pi API change doesn't ripple. No production risk; flagged as coupling cost.
### F-4: Process-wide mutable runtimeCache has no invalidation hook — test isolation & long-session staleness

- **Severity**: low
- **Lens**: Architect
`let runtimeCache: Promise<ModelRuntime> | undefined` (src/session-agent.ts) is module-level and keyed to nothing; it is created once per process and shared across every session-backend spawn. The inherit tests correctly vi.mock `ModelRuntime` (tests/session-agent-inherit.test.ts:65-80) so they don't hit it, but any future test path that lets `ModelRuntime.create()` run for real will cache a live runtime for the whole vitest process, and a long-lived TUI session that changes providers/settings mid-run will keep the stale catalog (compounding F-1's `allowNetworkRefresh=false` behavior). The rejection-clear-on-failure retry logic is good. Minor; consider a reset hook for tests and a comment on the no-mid-run-invalidation assumption.
### F-5: Inline doc comments over-reference internal AC-NN/SCENARIO-NNN/F-N/AR-NN tracking codes future maintainers lack the key for

- **Severity**: low
- **Lens**: Minimalist
Nearly every added/edited function carries a multi-paragraph comment citing SCENARIO-001/005/008, F-1/F-2, AR-02/AR-03, AC-04/AC-10, etc. This is consistent with the repo's existing house style (the surrounding code is equally verbose), so it is not a defect, but a minimalist lens flags that for a feature set this size the scenario-code cross-references add volume that adds little maintenance value once the spec directory is archived. Intent-first prose ('inherited wins over role default, loses to env/per-call') would carry the same information. No action required; noted for consistency-of-style awareness.
### F-6: Double-application guard is correct but split across two modules — invariant rests on a single truthy-check

- **Severity**: low
- **Lens**: Architect
The 'do not double-apply thinking' guarantee (SCENARIO-007) depends on `resolveExplicitThinking` (pi-spawn.ts, no role default) returning truthy exactly when an override exists, which then gates `if (!creationThinking) applyThinkingLevel(session, resolveThinking(...))` in runAgentViaSession. The logic is correct and is pinned by an existing invariant test ('session.setThinkingLevel is never called more than once for a single run', tests/session-agent-inherit.test.ts:164). No action — flagged only so the cross-module invariant is preserved during any future refactor of resolveExplicitThinking/resolveThinking's return semantics.
