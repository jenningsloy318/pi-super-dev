# Research Report: pi 0.82.x SDK modernization: model/thinking inheritance, constrained sampling for structured_output, typed registerEntryRenderer, and PI_* build-tagging

- **Date**: 2026-07-28
- **Author**: super-dev:research-agent

---

## Summary

Research against the pi 0.82.0/0.82.1 primary sources (repo CHANGELOG, pi-ai README, extensions.md, sdk.md, environment-variables.md, and the structured-output & custom-model SDK examples) confirms every required API is public and typed in the bumped 0.82.1 surface. Feature 1: createAgentSession({ model, thinkingLevel, modelRuntime }) accepts a resolved Model<any> AND a thinkingLevel as first-class creation options (canonical path); ctx.model is a live Model<any> with .id/.provider and ctx.modelRegistry can resolve ids via getModel(provider,id) (built-in) or modelRuntime.getModel() (incl. custom). Feature 2: ToolDefinition.constrainedSampling is typed false | { type:'json_schema'; strict:'prefer'|'require' } | { type:'grammar'; variants:{...} }; strict:'prefer' uses provider strict enforcement when supported and SILENTLY falls back to normal tool calling otherwise (verified via pi-ai's resolveStrictSampling: unsupported+'prefer' returns undefined, no throw; unsupported+'require' throws) — so missingKeys() is correctly retained as the fallback. Strict-capable JSON schema = object with required keys + additionalProperties:false (OpenAI & pi examples align); Optional keys and additionalProperties:true must NOT request strict. Feature 3: registerEntryRenderer<T>(customType, renderer) is public typed API in 0.82.1; EntryRenderer/EntryRenderOptions are exported from @earendil-works/pi-coding-agent. Feature 4: PI_SESSION_ID/PI_SESSION_FILE/PI_PROVIDER/PI_MODEL/PI_REASONING_LEVEL are injected into commands run by built-in/factory bash tools; values are resolved at command start, absent in user !/!! commands and SDK-embedded runs — read process.env defensively. Open Questions 1 and 2 are resolved; Question 3 (exact injection point) is a codebase-internal decision the research bounds but cannot finalize.

## Options Considered

### Feature 1 — Thread the live ctx.model as the primary inherited Model, resolve ctx.model.id via getModel/modelRuntime only as fallback (AC-01/02/04/08)

createAgentSession's model option expects a Model<any> instance, not an id string (sdk.md + 02-custom-model.ts). Simplest, no registry round-trip: when ctx.model is a live Model<any>, thread that instance directly through RunOptions (e.g. inheritedModel as Model<any> OR a resolved id + re-resolution at the session boundary). If the option chain must carry a string id (per AC-04 'resolve ctx.model.id to Model<any>'), resolve it at runAgentViaSession using getModel(provider,id) for built-ins (no auth check, synchronous, from @earendil-works/pi-ai) or modelRuntime.getModel(provider,id) to include custom models — both confirmed in sdk.md. Risk: getModel only knows built-ins; custom/proxy models need modelRuntime, which must be threaded in. Recommendation: thread ctx.model.id as the inherited string, and resolve to Model<any> at the session-creation boundary with a getModel→modelRuntime→undefined fallback that degrades to the SDK/settings default (never throws). Precedence explicit-param → SUPER_DEV_MODEL env → inherited id → SDK default is preserved by treating inherited as the lowest-priority non-default tier.
### Feature 1 — thinkingLevel: pass it as a createAgentSession option (canonical) and keep applyThinkingLevel() guarded as best-effort second defense (AC-03/04/07)

sdk.md shows createAgentSession({ thinkingLevel: 'medium' }) and session.setThinkingLevel(level) as the supported, clamped path (values: off|minimal|low|medium|high|xhigh|max; clamped to model capabilities). Passing thinkingLevel in createAgentSession options is the canonical single-application point. Keeping the existing applyThinkingLevel(session,...) as best-effort is reasonable for older runtimes BUT must be guarded against double-application (if the option already set it, skip or compare current level before re-applying). Recommendation: set thinkingLevel in createAgentSession when an explicit-or-inherited value exists; guard applyThinkingLevel to only fire when session.thinkingLevel !== resolved level. Widened resolveThinking precedence (per-call → SUPER_DEV_THINKING env → inherited ctx.thinkingLevel → role default) feeds this resolved value.
### Feature 2 — Use strict:'prefer' (never 'require') and gate on isStrictCapable(schema) = Object + >=1 required non-Optional key + additionalProperties:false (AC-06/07/08)

pi-ai README: strict:'prefer' enforces provider-side strict schema when supported and otherwise falls back to normal tool calling (resolveStrictSampling returns undefined, no throw); strict:'require' FAILS the request when unsupported. Since missingKeys()+corrective re-prompt is the deliberate fallback for non-capable providers (glm/local) and permissive schemas, 'prefer' is the only safe choice — it never raises and never breaks a run. OpenAI/pi strict requirements (OpenAI structured-outputs guide + pi edit_file/grammar examples) mandate an object schema, ALL relevant keys required (Optional emulated via type:["string","null"]), and additionalProperties:false at every object level. So isStrictCapable must return false for the current permissive controlSchema (all-Optional + additionalProperties:true) and for non-Object schemas — exactly AC-06. Build the strict variant as Type.Object({...required typed keys...}, { additionalProperties:false }) and attach constrainedSampling only when isStrictCapable is true; byte-identical behavior otherwise.
### Feature 3 — Call pi.registerEntryRenderer(customType, renderer) directly (typed); import EntryRenderer/EntryRenderOptions from the package root (AC-09/SCENARIO-014/015)

Confirmed in the real pi repo's extensions index.ts that EntryRenderer, EntryRenderOptions, and ToolDefinition are re-exported from @earendil-works/pi-coding-agent. registerEntryRenderer<T>(customType: string, renderer: EntryRenderer<T>): void is the public typed 0.82.1 signature (the prior as-unknown-as cast existed only because it was absent in 0.80.3). Delete the cast and the piWithRenderer shim; keep the existing try/catch best-effort guard (SCENARIO-015) and the durable background-summary transcript-card rendering. typecheck stays strict-clean because the types now resolve against the bumped ^0.82.1 surface.
### Feature 4 — Read process.env.PI_SESSION_ID / PI_MODEL defensively and inject a correlation header/field into build-gate captured output only when present (AC-10/SCENARIO-016/017)

environment-variables.md confirms PI_SESSION_ID/PI_SESSION_FILE/PI_PROVIDER/PI_MODEL/PI_REASONING_LEVEL are injected into commands run by built-in and factory-created bash tools (resolved at command start; absent for user !/!! commands and SDK-embedded runs). These vars are inherited by the build-gate's child processes, so reading process.env in build-runner is valid and never throws. To keep print/json/rpc/headless modes byte-clean, add the correlation data as a structured metadata field or a clearly-delimited header line that is emitted ONLY when the vars are present (absent → byte-identical to today). Recommendation: a single guarded 'PI_SESSION_ID=… PI_MODEL=…' correlation line/field appended to the captured build log or a structured-trace field; gate pass/fail and command construction must be untouched (observability-only).

## Open Issues

- RESOLVED (was OQ-1, model inheritance source): createAgentSession.model expects a Model<any> instance. The live ctx.model can be threaded directly (simplest) OR its .id resolved via getModel(provider,id) (built-ins, sync, no auth check) / modelRuntime.getModel(provider,id) (incl. custom). If RunOptions carries a string inheritedModel per AC-04, resolution must happen at the session boundary with getModel→modelRuntime→undefined fallback so it never throws (SCENARIO-008). Implementation-stage detail: whether to thread the Model instance or the id string through RunOptions is a codebase call; research confirms both paths are supported.
- RESOLVED (was OQ-2, constrainedSampling fallback): pi-ai's resolveStrictSampling shows strict:'prefer' returns undefined (normal tool-calling fallback, no throw) when the provider/model cannot honor it; only strict:'require' throws. So missingKeys()+corrective re-prompt remains the correct fallback and will still fire on non-capable providers (glm/local) and permissive schemas. Use 'prefer' exclusively.
- STILL AMBIGUOUS (was OQ-3, Feature 4 injection point): research confirms the PI_* env vars exist and are inherited by build-gate child processes, but whether to inject a correlation line into captured stdout/stderr (flows through sink.log → live transcript + run log) vs a dedicated structured-trace field is a codebase-internal decision requiring inspection of build-runner/gates.ts result shape. The byte-clean + observability-only constraints bound it to: emit only when vars present, never touch pass/fail or command construction. Recommend the next stage inspect gates.ts to choose header-line vs structured-field so machine-readable modes stay byte-identical.
- MINOR (verify in repo): ctx.thinkingLevel availability on the super_dev tool's execute() ctx. Research confirms ctx.model is on ExtensionContext and thinkingLevel_select events carry levels, and pi.getThinkingLevel()/session.thinkingLevel exist; the requirement asserts ctx.thinkingLevel is readable in the tool ctx. If the tool-execute ctx lacks a thinkingLevel field, fall back to reading it via the session/runtime accessor — implementation stage should confirm the exact ctx shape (no-throw if undefined, per SCENARIO-002).
