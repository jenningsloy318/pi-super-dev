# Requirements: Modernize pi integration: inherit main-session model/thinking, constrained sampling for structured_output, typed registerEntryRenderer, bash session-env tagging

- **Date**: 2025-11-19
- **Author**: super-dev:requirements-clarifier
- **Type**: enhancement
- **Priority**: high
- **Status**: draft

---

## Executive Summary

Adopt pi 0.82.x features as one cohesive change set across the pi-super-dev extension. The highest-leverage change makes every spawned specialist inherit the main session's model and thinking level (today extension.ts ignores ctx.model/ctx.thinkingLevel, so a user on Opus+xhigh gets role-default specialists). It also enables strict JSON-schema constrained sampling on the structured_output tool for capable providers (keeping the missingKeys corrective re-prompt as the fallback), removes the registerEntryRenderer capability cast now that it is typed in 0.82.1, and tags build-gate runs with pi's PI_SESSION_ID/PI_MODEL env vars for parallel-run correlation. All changes are additive, preserve the no-throw/best-effort discipline, and keep print/json/rpc/headless modes byte-clean.

## Acceptance Criteria

- **AC-01**: In src/extension.ts, inside the super_dev tool's execute(), ctx.model?.id and ctx.thinkingLevel are read BEFORE runPipelineTask(...) and threaded as DEFAULTS through RunOptions (e.g. inheritedModel / inheritedThinking) so that an explicit params.model or SUPER_DEV_MODEL / SUPER_DEV_THINKING env var still overrides them. Nothing throws when ctx.model / ctx.thinkingLevel are undefined (older or non-TUI ctx) — execution degrades to current behavior.
- **AC-02**: Model precedence is enforced end-to-end as: explicit params.model → SUPER_DEV_MODEL env (added to resolveModel if absent) → inherited ctx.model.id → SDK/settings default. The existing buildSpawnArgs behavior is preserved: --model is pushed only when a model is actually resolved.
- **AC-03**: resolveThinking() in src/pi-spawn.ts precedence chain is widened from (per-call → SUPER_DEV_THINKING env → role default) to (per-call → SUPER_DEV_THINKING env → INHERITED main-session ctx.thinkingLevel → role default). inheritedThinking is threaded through SpawnAgentOptions / SessionAgentOptions and from workflow.ts's realAgent (options.inheritedThinking).
- **AC-04**: In src/session-agent.ts runAgentViaSession, createAgentSession({ ... }) is given the resolved model via the SDK's model?: Model<any> option AND thinkingLevel directly as a createAgentSession option when an explicit-or-inherited value is available. applyThinkingLevel(session, ...) is retained as a second/best-effort line of defense but guarded against double-application. Note: model inheritance requires resolving ctx.model.id to a Model<any> — falls through to the SDK/settings default if the id cannot be resolved.
- **AC-05**: When super_dev is invoked WITHOUT explicit model/thinking params on a capable session, every spawned specialist on BOTH the session and subprocess backends uses the inherited model and a thinking level no LOWER than the role default would have been (inherited wins over role default; per-call/env still win). A new test asserts inheritedThinking flows from makeContext/realAgent into the agent call (e.g. a workflow test), and resolveThinking gets a precedence test covering the new inherited tier.
- **AC-06**: A small isStrictCapable(schema) helper is introduced (returns true only when the schema is a TSchema Object with at least one REQUIRED non-Optional key and additionalProperties: false). isStrictCapable is false for the current permissive controlSchema (all-Optional + additionalProperties: true) and for open/unknown-key schemas. It is unit-tested for required-keys, all-Optional, additionalProperties:true, and non-Object cases.
- **AC-07**: When the caller passes a real strict-capable schema (opts.schema) OR controlKeys can be built into a strict schema (Type.Object of required typed keys, additionalProperties: false), the structured_output tool (structuredOutputTool) sets constrainedSampling: { type: "json_schema", strict: "prefer" } — typed against the 0.82.1 ToolDefinition.constrainedSampling field. constrainedSampling is NEVER attached to a permissive schema (isStrictCapable gates it). The permissive Type.Optional(Type.Any()) + additionalProperties:true shape remains ONLY as the fallback for open/unknown-key schemas.
- **AC-08**: The missingKeys() + single corrective re-prompt turn machinery in session-agent.ts is PRESERVED unchanged as the fallback for non-capable providers (glm/local) and permissive schemas where strict constrained sampling is not applicable. A test asserts constrainedSampling is attached only when isStrictCapable(schema) is true (and absent otherwise — byte-identical behavior).
- **AC-09**: The registerEntryRenderer capability cast in src/extension.ts (const piWithRenderer = pi as unknown as {...}) is DELETED. activate() now calls pi.registerEntryRenderer(...) directly with the proper typed signature registerEntryRenderer<T>(customType: string, renderer: EntryRenderer<T>): void, importing EntryRenderer / EntryRenderOptions from @earendil-works/pi-coding-agent where helpful. The existing try/catch best-effort guard and the durable background-summary transcript card rendering behavior are unchanged.
- **AC-10**: In the build gate (src/build-runner/gates.ts and/or its spawn path), when process.env.PI_SESSION_ID and/or process.env.PI_MODEL are present, the captured build-run log/trace/artifact metadata includes them (e.g. a correlation header line prepended/appended to the captured build log, or a field in any structured trace). When the env vars are absent the build run is byte-identical to today. Gate pass/fail logic and command construction are unchanged; a focused test covers present and absent cases.
- **AC-11**: CHANGELOG.md gains a concise [Unreleased] entry summarizing Features 1–4 (inherit main-session model/thinking; constrained sampling for structured_output; typed registerEntryRenderer; bash session-env tagging), noting the ^0.82.1 dependency bump is already done.
- **AC-12**: npm run typecheck is strict-clean against the 0.82.1 types, and the full vitest suite (existing 1437 tests + all new tests added for AC-05, AC-06, AC-08, AC-10) is green.

## Non-Functional Requirements

- No-throw / best-effort discipline: every new code path (reading ctx.model/ctx.thinkingLevel, resolving model to Model<any>, applying thinkingLevel, attaching constrainedSampling, reading PI_* env vars, registerEntryRenderer) must swallow failures and degrade to current behavior rather than abort a run.
- Zero-ANSI byte-clean contract: print / json / rpc / headless modes must remain byte-identical — the dashboard widget, status pills, constrainedSampling header lines, and PI_* tagging must NOT emit ANSI or alter machine-readable output in those modes.
- Additive-only, never-clobber: model/thinking inheritance must NEVER override an explicit user/LLM params.model, a SUPER_DEV_MODEL / SUPER_DEV_THINKING env var, or a per-call thinking override. Inheritance is a fallback tier only.
- Strict JSON-schema correctness: constrainedSampling strict:"prefer" is requested ONLY on genuinely strict-capable schemas (required non-Optional keys + additionalProperties:false); never on permissive schemas to avoid provider no-ops or confusion.
- Type safety: no new as unknown as casts; the registerEntryRenderer call uses the public 0.82.1 typed API and constrainedSampling is typed against ToolDefinition.
- Observability-only change for Feature 4: PI_* tagging must not influence gate pass/fail, command construction, or timeout behavior; it only enriches captured build-run metadata.

## Open Questions

- Model inheritance (AC-04): ctx.model is a Model<any> with a string id, but createAgentSession's model option expects a Model<any> (not just an id string). Should the inherited model be passed by re-using ctx.model directly (the live Model instance) when available, or by resolving ctx.model.id back to a Model via the SDK's model registry? Re-using ctx.model is simplest and avoids a registry round-trip, but the task text mentions ctx.model.id — confirm the preferred source.
- ConstrainedSampling fallback semantics (AC-07): on a capable provider with strict:"prefer" that the model cannot honor, does pi silently fall back to normal tool calling (so missingKeys still fires), or could it raise? The AC assumes graceful fallback; verify against pi 0.82.1 runtime behavior for at least one capable provider.
- Feature 4 location: the build gate (src/build-runner/gates.ts) currently returns structured results (stdout/stderr) rather than writing a trace file to disk. Is the intended 'build-run log/trace/artifact' the captured gate stdout/stderr that flows into the live transcript + run log (via sink.log), a dedicated on-disk build trace, or both? Confirm where the correlation header should be injected so it is observable without altering gate logic.
