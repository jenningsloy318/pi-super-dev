## Findings

### F1: Feature 2 constrained sampling is wired but inert in production — no stage schema is strict-capable

- **Severity**: Medium
- **File**: `src/render/schemas.ts; src/session-agent.ts`
The acceptance criterion for Feature 2 is that "on a capable provider, a stage with a well-defined required-key schema gets strict:prefer and the corrective re-prompt rarely fires." The gating helper `isStrictCapable` is correct (requires a typebox Object with ≥1 required non-Optional key AND `additionalProperties === false`), and `structuredOutputTool` attaches `constrainedSampling: { type:"json_schema", strict:"prefer" }` only when it holds. However, `isStrictCapable` returns false unless `additionalProperties === false`, and EVERY render schema that actually flows into `call.schema` (CodeReviewData, SpecReviewData, AdversarialReviewData, ImplementationSummaryData, DesignData, …) is a bare `Type.Object({...})` with NO options spread — TypeBox omits `additionalProperties` by default, so `obj.additionalProperties !== false` is true and `isStrictCapable` returns false for all of them. The new `strictControlSchema` helper is defined and unit-tested but is NOT consumed by any stage. Net effect: in production, `constrainedSampling` is NEVER attached, the model is never forced to fill keys, and `missingKeys()` + the corrective re-prompt fire exactly as before — i.e. the feature delivers zero realized benefit; it is scaffolding + tests only. Failure scenario: a capable-provider run of the code-review/adversarial/spec-review stages still routinely omits keys and burns a corrective turn, exactly the cost Feature 2 was meant to eliminate. Fix: amend the well-defined render schemas with the options spread, e.g. `Type.Object({ title: Type.String(), date: Type.String(), verdict: Type.String(), summary: Type.String(), findings: Type.Array(Finding) }, { additionalProperties: false })` for CodeReviewData/SpecReviewData/AdversarialReviewData/ImplementationSummaryData (verify nested `Finding`/array element Objects are also closed if the provider's strict mode recurses), or have the verify/implementation stages pass a `strictControlSchema(keys)` variant. Confidence ~0.85 (confirmed: `grep -c 'additionalProperties: false' src/render/schemas.ts` → 0).
### F2: resolveSessionModel fallback performs a type-unsound `as SessionModelOption` cast on an incomplete object

- **Severity**: Medium
- **File**: `src/session-agent.ts`
- **Line**: resolveSessionModel catch branch (~150-175)
When `ModelRuntime.create()` throws (older runtime / mocked SDK), `resolveSessionModel` falls back to `return { id: modelId || id, provider } as SessionModelOption;` where `SessionModelOption = NonNullable<…createAgentSession…['model']> = Model<any>`. `Model<any>` is a large interface (id, provider, api, endpoint, auth, headers, thinkingLevelMap, …). The cast is accepted by TS only because `Model<any>` is assignable to `{id,provider}` (the `as` direction TS permits), but at runtime the object is missing every other required field. If this fallback path is taken in production and the SDK touches any field beyond `id`/`provider`, `createAgentSession` throws in a confusing, non-obvious way (the error will not mention the incomplete descriptor). The outer try/catch in `runAgentViaSession` catches it and returns an error `SpawnResult`, so it degrades rather than crashes — but the inherited-model feature then silently fails for any environment where `ModelRuntime.create()` is unavailable. Failure scenario: a real install whose runtime cannot initialize surfaces agent errors of the form 'cannot read X of undefined' on the model object instead of cleanly falling back to the settings default. Fix: in the catch branch `return undefined;` (let createAgentSession omit `model` entirely and use the SDK/settings default), matching the documented 'fall through to SDK/settings default' contract for the unknown-id case. Confidence ~0.6 (UNCERTAIN — depends on how often `ModelRuntime.create()` throws in real installs; the primary path is sound).
### F3: Inherited model id assumed to be `provider/model-id` form; a bare id degrades silently

- **Severity**: Low
- **File**: `src/session-agent.ts:splitModelRef; src/pi-spawn.ts:resolveModel`
`resolveSessionModel` calls `splitModelRef(id)` which splits on the FIRST '/'; a bare id with no slash yields `{ provider: <whole id>, modelId: "" }`, then `runtime.getModel(provider, "")` is unlikely to match and the resolution falls through to the SDK default. Separately, the subprocess backend pushes `--model <inherited id>` verbatim, which is correct only if pi accepts whatever form `ctx.model.id` takes. The Feature 1 acceptance ("every spawned specialist uses that model") therefore depends on `ctx.model.id` already being in `provider/model-id` form; if pi's `Model.id` is a bare slug, inherited-model resolution silently no-ops on the session backend and may produce an unusable `--model` on the subprocess backend. Failure scenario: user on a non-default model runs `/super-dev` with no model arg; specialists silently fall back to the settings-default model rather than the live session model. Fix: confirm pi's `Model.id` format empirically and either document the assumption, or resolve via `ModelRuntime` by the full id (without splitting) when no slash is present. Confidence ~0.5 (UNCERTAIN — behavior hinges on pi's id convention, which was not verifiable from the installed .d.ts surface).
### F4: Spec ambiguity: 'inherited no lower than role default' vs 'inherited wins over role default' — implementation chose the latter

- **Severity**: Low
- **File**: `src/pi-spawn.ts:resolveThinking; src/session-agent.ts`
Feature 1's acceptance says specialists use "a thinking level no LOWER than the role default would have been (inherited wins over role default, …)". These two clauses conflict: if the main session is on `low` and a `design` agent (role default `high`) is spawned, 'inherited wins over role default' yields `low`, which IS lower than the role default — violating the 'no lower' clause. The implementation correctly and consistently implements the explicit precedence chain (per-call → env → INHERITED → role default) on both backends, so `low` wins for `design`. This is internally consistent and matches the authoritative precedence text, so it is flagged only as a spec-ambiguity heads-up, not a defect. If the 'no lower than role default' intent was the real requirement, the fix would be to max(inherited, role-default) at the role-default tier. Confidence ~0.7.
### F5: CHANGELOG describes a build-log header line that the implementation does not emit

- **Severity**: Info
- **File**: `CHANGELOG.md; src/build-runner/gates.ts`
The [Unreleased] entry states the build gate 'stamps a plain-ASCII `# pi-session=<id> model=<model>` correlation tag into the captured build-run metadata'. The actual implementation adds ONLY the additive `correlation?: { sessionId?; model? }` field on `BuildGateResult` — there is no header line prepended to `ran`/`errors` or any captured log (gates.ts does not itself persist a build log; it returns a structured result). The spec's 'a header line in the captured build log and/or an additive correlation field' uses 'and/or', so the field alone satisfies the contract and AC-10/SCENARIO-016,017 pass. Minor doc/impl wording drift only; consider softening the changelog to 'records a correlation tag in the build-run result metadata'. Confidence ~0.9.
