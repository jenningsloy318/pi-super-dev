# Debug Analysis: super-dev fails silently on unrecoverable blockers: escalation is wired at the run boundary, where failure context is already lost

- **Date**: 2026-07-28

---

## Summary

super-dev has two distinct "silent failure on unrecoverable blocker" paths, both caused by the same architectural gap: human-escalation (HITL) is wired ONLY at the RUN BOUNDARY (`extension.ts` `execute()` catch + the post-run `handleStagnation`), by which point the failure context needed to pause-and-continue has already been destroyed. (1) FATAL-GATE EXHAUSTION: `src/nodes.ts` `gate({fatal:true})` unconditionally `throw new FatalAbort(msg)` at line 436 with NO escalation hook before it. `FatalAbort` carries only the `msg` string. It re-throws through every tolerant `sequence`/`catch` (nodes.ts:172, :202, :550) and surfaces in `execute()`'s `catch (err)` which returns `{isError:true, details:{}}` — no `ctx.ui.select` prompt ever fires, and `state.setup.specDirectory`/`worktreePath` are no longer reachable. (2) VERIFY-LOOP STAGNATION: `src/stages/verify.ts` stamps `state.__stagnated` (line 167) / `state.__testStagnated` (line 329) and BREAKS the loop inline, but the ONLY escalation, `handleStagnation`, is invoked AFTER `runPipelineTask` returns in `execute()` (`const escalationChoice = await handleStagnation(summary, ctx)`). At that boundary the verify loop body is gone, so even an interactive choice can only finish/re-run — it can never "retry-with-guidance" inline. The fix (already designed in the task) threads an `escalate(failure)` callback from `execute()` → `RunOptions` → `StageContext` (mirroring the working `userSteerProvider` pattern) and fires it INLINE at each unrecoverable point (inside the gate loop immediately before the `throw FatalAbort`; inside the verify loop when stagnation is detected), where the live `state`/worktree/specDirectory are still in scope. CRITICAL FIX-DEPENDENCY GAP: the task asserts `rollbackWorktreeTo(worktreePath)` "ALREADY EXISTS in src/tracking.ts (just added)" — it does NOT (grep of src/ returns nothing; latest commit `35806b37` is mid-run-context, not rollback). The recovery action for "retry-with-guidance" therefore depends on a helper that must actually be created, not merely wired. The other reused infrastructure is confirmed present and working: `appendUserNotes`/`userNotesForAgent` + `.user-notes.json` (`src/render/user-notes.ts`), the drain seam in `workflow.ts` `realAgent` (lines 148-149), the `userSteerProvider` threading pattern (types.ts:318 → workflow.ts makeContext → realAgent), and `createMemoizingAgent` (workflow.ts:213) which only caches completed calls (a thrown gate is uncached, so an inline retry re-runs it).

## Root Cause

The silent failure is an architectural lifecycle mismatch, not a missing UI call. Human escalation is reachable ONLY at the run boundary — `execute()`'s `catch (err)` (which returns `{isError:true, details:{}}` with no prompt) and the post-run `handleStagnation(summary, ctx)` call. Both fire AFTER the failure context that a pause-and-continue needs has been destroyed: (a) a `FatalAbort` thrown at `src/nodes.ts:436` carries only the `msg` string, having already discarded `state.setup.specDirectory`, `state.setup.worktreePath`, and the in-progress `state`; (b) a stagnant verify loop has already `break`-ed out of `reviewLoopUntil`/the integration loop (`src/stages/verify.ts:167`, `:329`), so its loop body is gone and an interactive choice can no longer re-enter it. The pi pause-and-continue pattern (`await ctx.ui.select` blocking the running flow, then continuing inline) REQUIRES the failure context to be live where the decision is made — which is true INSIDE the gate loop and INSIDE the verify loop, NOT at the boundary. Exact locations: fatal throw at `src/nodes.ts:436` (`if (opts.fatal) throw new FatalAbort(msg);`) needs an `escalate` call immediately before it; stagnation stamps at `src/stages/verify.ts:167` and `:329` need an inline `escalate` call (instead of just stamping+breaking) so the loop can `continue` on a retry decision. The fix threads `escalate?: Escalate` onto `RunOptions` (`src/types.ts:276`, mirroring `userSteerProvider` at line 318), through `makeContext` (`src/workflow.ts:108`) onto `StageContext` so `ctx.options.escalate` is callable from inside gates/stages, and supplies it from `execute()` (which owns `ctx.ui`). SECONDARY FIX-DEPENDENCY GAP: the recovery helper `rollbackWorktreeTo` asserted to already exist in `src/tracking.ts` does NOT exist and must be created (git reset --hard + git clean -fd, scoped to the super-dev worktree, never-throws) before AC-05's retry path can work.
