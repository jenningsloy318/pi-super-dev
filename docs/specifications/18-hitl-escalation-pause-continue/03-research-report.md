# Research Report: External research for HITL escalation (pause-ask-continue via ctx.ui) in super-dev

- **Date**: 2026-07-28
- **Author**: super-dev:research-agent

---

## Summary

Online research confirms the locked design maps cleanly onto pi's documented extension API. The pi extensions docs (SRC-01) define exactly the primitives the escalate callback needs: `ctx.ui.select(message, options, {timeout})`, `ctx.ui.input(prompt, placeholder)`, `ctx.ui.confirm(...)`, and `ctx.ui.notify(...)`; these dialog methods are guarded by `ctx.hasUI` (true in TUI **and** RPC modes, false in print/json) and return a benign value on timeout/dismissal — `select()`→`undefined`, `input()`→`undefined`, `confirm()`→`false` (SRC-01) — which is the exact contract `Escalate = (failure) => Promise<EscalationDecision | undefined>` (AC-02, SCENARIO-003) requires, with zero additional wrapping needed for the no-throw case. Notably the design's choice of `select`/`input` over `ctx.ui.custom` is vindicated: `custom()` is TUI-only (`ctx.mode==="tui"`) and the pi-subagents `clarify` model that uses it has a documented footgun (issue #385, SRC-04) where a `custom` overlay fired mid-in-flight-tool-call returns falsy/unconfirmed almost immediately and silently degrades to 'cancelled'; `select`/`input` work in RPC too and degrade benignly, so the escalate path sidesteps that trap. The HITL pattern catalog (SRC-05) and the Interruptible-Agent-Execution pattern (SRC-06) validate pause-and-continue over abort-and-rerun: 'identify the boundary, pause the loop, surface the proposed action with context, require explicit approve/reject, resume on approve / abort-or-replan on reject, log the decision' — a 1:1 match for the retry/revise/accept/abandon choice set (AC-06) and the always-write-report observability (AC-07). For rollback (AC-05), the runaway-agent rollback playbook (SRC-07) and the 'why git reset --hard is the wrong tool for agent pipelines' analysis (SRC-08) both prescribe worktree-scoped, surgical `git reset --hard <known-good>` + `git clean` that never touches the main checkout, plus commit-often for a rich reflog and bounded retry before falling back — directly supporting `rollbackWorktreeTo` and the bounded-cap (AC-09) decision. Finally, production TypeScript fault-tolerance guidance (SRC-09) endorses the no-throw/degrade-to-fail-with-report shape (AC-10) as the idiomatic 'error boundary / graceful degradation' pattern at a framework boundary, and supplies a concrete `withRetry(fn, isRetryable, maxAttempts)` shape with an `isRetryable` predicate and exponential-ish backoff that fits AC-09's dedicated-cap recommendation.

## Options Considered

### Block on ctx.ui.select + ctx.ui.input (NOT ctx.ui.custom) — the pi-subagents clarify model is the wrong primitive here

PROS (grounded in SRC-01 pi extensions.md): `select`/`input`/`confirm` are dialog methods explicitly guarded by `ctx.hasUI`, which is true in BOTH TUI and RPC modes (false only in print/json) — so interactive escalation is default-on in TUI AND RPC per AC-08, and print/json/headless short-circuit to report+fail. They support a `{timeout}` option with a live countdown and return benign values on timeout/cancel (`select`→`undefined`, `input`→`undefined`, `confirm`→`false`) — a perfect match for `Promise<EscalationDecision | undefined>` and the 'dismissal/timeout yields no decision and never throws' requirement (AC-02, SCENARIO-003); the escalate impl still wraps in try/catch as defense-in-depth but the API itself already cannot throw on dismissal. CONS: less custom layout than a full TUI component. WHY NOT custom(): SRC-04 (pi-subagents #385) documents that `ctx.ui.custom` is TUI-only and, when pushed as an overlay from inside an in-flight synchronous tool call, returns falsy/unconfirmed almost immediately and silently degrades to 'Chain cancelled' — exactly the silent-fail the spec is trying to eliminate. The escalate path fires INLINE before throwing (not inside an LLM-invoked tool call), and uses select/input, so it sidesteps this trap. Serves AC-02, AC-08, SCENARIO-003, SCENARIO-018, SCENARIO-019.
### Bounded retry: a dedicated, small escalation-retry cap (e.g. 2) per blocker with an isRetryable-style predicate, NOT reuse of each gate's attempts/times cap

Grounded in SRC-09 (TS error handling: `withRetry(fn, isRetryable, maxAttempts)` with a predicate that keeps retry scope tight and a hard `maxAttempts` before surfacing the error) and corroborated by SRC-08 (KAOS cascade pattern: one bad fix → 4 failures; the answer is a bounded number of surgical restore→retry cycles before falling back, never unbounded spend). PROS of a dedicated cap: decoupled from each gate's own retry semantics (a gate's `times` cap is tuned for transient model flakiness, not for human-guided retries), trivially bounded so the run can never loop infinitely or spend unbounded agent budget (AC-09, SCENARIO-020), and the firing point tracks its own count so the fallback to revise-manually/abandon (SCENARIO-021) is a single clear branch. CONS: introduces one new piece of per-firing-point state. REUSE-the-gate-cap alternative is simpler but couples escalation budget to gate internals and risks an unexpectedly large cap. The `isRetryable`-predicate idea also cleanly encodes AC-06's 'accept-limitation offered only for soft blocks': hard build failures are non-retryable/terminal, soft review/test findings are retryable-or-acceptable. Serves AC-09, AC-06, SCENARIO-020, SCENARIO-021.
### Rollback = worktree-scoped `git reset --hard <known-good> HEAD` + `git clean -fd`, never-throw, with main checkout provably untouched (matches the locked rollbackWorktreeTo helper)

Grounded in SRC-07 (runaway-agent rollback playbook: worktree-per-session contains the damage; `git reset --hard HEAD@{1}` or a known-good commit, or `git reset --hard origin/main` if no commits yet; the main worktree is untouched and the session worktree can be thrown away; commit-often keeps the reflog rich) and SRC-08 (surgical, per-agent restore beats repo-wide `git reset --hard`; an unbounded/naive reset 'blows up every other agent's work'). The git docs (SRC-10 git-clean, SRC-11 git-reset, SRC-12 git-worktree) confirm `git clean -fd` removes untracked files/dirs in the current working tree only and `git reset --hard` rewrites the working tree to a commit — both scoped to the worktree's own HEAD, never the main checkout. PROS: surgical, fast, no new infra, matches the existing helper contract and AC-05/SCENARIO-010's 'strictly confined to the super-dev worktree, never touches the user's main checkout'. CONS (to mitigate): a non-git/missing worktree must not crash the run — so wrap in never-throw (AC-10, SCENARIO-012: rollback failure still allows retry); prefer resetting to a known-good commit (the worktree's pre-stage HEAD) rather than bare `HEAD` if the agent has already committed partial work, to avoid losing salvageable progress. Serves AC-05, AC-10, SCENARIO-010, SCENARIO-012.
### Fault-tolerance shape: best-effort try/catch per escalation-path step that degrades to fail-with-report (NOT a full Result<T,E> rewrite of the pipeline)

Grounded in SRC-09 (TypeScript error handling in production): at framework/integration boundaries the idiomatic choice is an error-boundary-style never-throw wrapper that degrades gracefully (substitute a safe default / fail-with-report), reserving full discriminated-union Result<T,E> threading for internal service layers; the article is explicit that 'middleware and framework boundaries' and 'graceful degradation by substituting a safe default' are where try/catch+degrade is correct, and that the escalate callback / report-write are exactly such best-effort side steps. PROS: minimal, non-invasive — keeps the existing FatalAbort-as-abort-signal semantics intact (AC-03/AC-06 still throw FatalAbort on 'abandon'), while each escalation-path step (callback, rollback, report-write) is individually wrapped so ANY failure degrades to fail-with-report and never crashes (AC-10, SCENARIO-022, SCENARIO-023). CONS: less type-safe than Result threading; mitigated by keeping the EscalationFailure/EscalationDecision types themselves as tight discriminated unions (AC-01) so the decision branch is exhaustive. This matches the spec's 'no-throw / best-effort everywhere' NFR precisely. Serves AC-01, AC-10, SCENARIO-022, SCENARIO-023.

## Open Issues

- ISS-01 (RPC-mode interactivity): SRC-01 confirms `ctx.hasUI` is true in BOTH TUI and RPC, and lists `select`/`input`/`confirm` as dialog methods that work under that guard — but also notes 'In RPC mode, some TUI-specific methods are no-ops or return defaults.' The pi RPC docs page (https://pi.dev/docs/latest/rpc) returned HTTP 404 when fetched, so it could NOT be confirmed whether `ctx.ui.select`/`ctx.ui.input` in RPC mode actually surface a prompt to the RPC client and await a real answer, or silently no-op/return `undefined` (which would make RPC sessions effectively informative-only despite `hasUI===true`). This directly affects AC-08's claim that 'interactive TUI/RPC sessions escalate by default' — TUI is confirmed, RPC is plausible-but-unverified. Recommend the code-assessment stage confirm against the installed `@earendil-works/pi-coding-agent` RPC UI protocol (the extensions.md links it as rpc.md#extension-ui-protocol) or that the impl guard escalation on `ctx.mode !== 'json' && ctx.mode !== 'print'` rather than `ctx.hasUI` alone if RPC no-ops are a risk.
- ISS-02 (rollbackWorktreeTo existence): The requirements doc's own open question is corroborated by research scope — nothing external resolves whether `rollbackWorktreeTo` already exists in src/tracking.ts or must be ADDED by this work. Research provides the canonical implementation shape (worktree-scoped `git reset --hard <known-good HEAD>` + `git clean -fd`, never-throw) either way, but AC-05's framing ('wire to existing' vs 'add + wire') depends on a codebase check, not external knowledge.
- ISS-03 (timeout return-value parity across modes): SRC-01 documents the benign return values (`select`→`undefined`, `input`→`undefined`, `confirm`→`false`) for TUI timed dialogs. Whether these hold identically when the underlying transport is RPC (disconnected/never-answering client) is not stated in the fetched docs; the escalate impl's try/catch + `undefined` fallback is safe regardless, but a test asserting 'timeout/dismissal → undefined' should cover the mode that will actually be used in CI.
