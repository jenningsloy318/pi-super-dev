## Q1 — How mature CI/CD systems classify and route environmental vs product failures

Mature systems uniformly **separate sensing from treatment**: the observed outcome and the pipeline's response to it are distinct fields, and a cheap deterministic classifier sits between them. GitHub Actions' `continue-on-error` is the canonical small example: a step that fails while `continue-on-error: true` records `outcome: failure` but `conclusion: success` [SRC-01] — "what happened" and "how the pipeline treats it" are different variables, so routing can be decided without lying about the evidence. The same system carries a *multi-class terminal taxonomy*, not a binary pass/fail: the Checks API's `conclusion` enum includes `failure`, `cancelled`, `timed_out`, `action_required`, `stale`, `skipped`, `neutral` [SRC-03] ⚠️ — distinct terminal classes that downstream routing (merge gates, required checks, paging) keys off. GitHub also standardizes an *annotation channel* (`::error` / `::warning` / `::notice` workflow commands with `title=`, `file=`, `line=` properties [SRC-02]) whose whole point is that a failure report is only useful if it **names a class and a location** — precisely R-N2's actionable-verdict rule.

Bazel's contribution is the same separation at test level. `--flaky_test_attempts=N` retries a failing test up to N times, and a test that passes on retry is marked **`FLAKY`**, a distinct status from `PASSED` or `FAILED` [SRC-05] ⚠️ — the retry budget is per-class (flakiness) and the outcome records that the class was involved, so dashboards can route flakes differently from regressions. Test *results* are cached only when they pass, keyed on the test action's declared inputs and environment (`--test_env` variables enter the action key) [SRC-04][SRC-13]. Bazel additionally supplies a quarantine-of-scope primitive: `tags = ["manual"]` excludes a target from wildcard expansion (`bazel test //...`) while keeping it buildable [SRC-06] — the failing thing is *excluded from the gate*, not deleted or "fixed". This repo's gates already contain the embryo of this sense/decide split: `resolveInScopePassWithBaseline` (src/build-runner/gates.ts:505–552) distinguishes the historical lenient-formula `inScopePass` from the baseline-verified one and appends a synthetic `[baseline-verify] regression — …` block — what is missing is a class label and a routing consequence, which is exactly AC-01/AC-05.

Go's `go test` closes the loop on environment-vs-product: results are cached **only on success** ("test results are cached only if the test passes; a failing test is always re-run") with a cache key over the test binary, flags, file contents, and the *values of environment variables the test actually reads* (`os.Getenv` records var+value into the key); `-count=1` is the documented cache bypass; cached passes print `(cached)` in place of timings [SRC-07]. Two adoptions fall out: (a) the `(cached)`/`[cached]` marker is a *provenance decoration*, not signal — it is one of the noise classes run 01-02-50's signature hash choked on; (b) a system that can't enumerate its environment inputs must refuse to cache (or invalidate aggressively) rather than cache over an unpinned environment.

**What we adopt (PRA):** outcome-vs-conclusion separation → AC-01's pure classifier over `BuildGateResult` before actuator selection; multi-class verdict taxonomy {environmental-blocker, product-defect, unclassified} mirroring Checks/Bazel status enums; the `FLAKY`-style named retry budget → AC-03's *exactly one* quarantine+re-gate; Bazel's `manual`-tag quarantine-by-exclusion → stash-based exclusion of foreign dirt; Go's success-only caching + env-in-key → AC-06 noise stripping and the AC-03 memo-bypass rule.

## Q2 — Failure-signature normalization precedents: what to strip and why

Sentry is the largest industrial deployment of failure-signature normalization. Every event gets a *grouping hash*; events with matching hashes collapse into one issue. The default grouping hierarchy prefers the most stable identity first — stack-trace frames (module/function/context), then exception type+value, then message templates — and users can force merge or split via **fingerprints** (SDK-side `event.fingerprint` array or server-side fingerprint rules using the `{{ default }}` placeholder) and, more recently, *grouping enhancements* that strip or replace volatile substrings **before** the hash is computed [SRC-08] ⚠️ exact page paths from memory. Sentry's own documentation warns that coarse fingerprints **over-group** — collapsing genuinely distinct errors into one issue — which is the exact two-sided hazard AC-08 pins in both directions (noise-only differences MUST compare equal; package/path or error-class differences MUST NOT). The stripping happens *before* hashing for the same reason SCENARIO-015 exists: normalization applied after truncation lets noise displace signal.

The test-infra world (Bazel, TestGrid in k8s test-infra, Chromium's flakiness dashboards) anchors identity on **structured keys, not raw output**: TestGrid's grid is (test name × build) and "flaky" means *same key, differing outcomes across runs* [SRC-14] ⚠️; Bazel's `--runs_per_test` / `--flaky_test_attempts` detect flakes by target label. Raw-log fingerprinting is used only where structure is absent — and when it is, the stripped-noise set is remarkably consistent across systems: timestamps (wall clock, zero discriminative power), durations (machine-load-dependent), run/trace/UUID identifiers (unique by construction — keeping them makes every failure a singleton), hostnames, ports/memory addresses, iteration counters, and cache markers. The invariant is the one PRB encodes: **strip everything that varies across executions of the same fault; keep everything that discriminates between faults** (failing subject paths, test names, error class, baseline SHA).

This repo's pre-fix normalizer is the degenerate case: `normalizeSignatureText` (src/stages/implementation.ts:68–70) collapses whitespace, trims, and caps at 800 chars — it normalizes *format*, not *volatility*, so `failureSignature` (implementation.ts:76–79) hashed 11 copies of the same snow failure into 11 distinct strings and `repeatedNoProgress`'s any-history exact match (implementation.ts:101–112) never fired. One subtle repo-grounded aggravator: the baseline memo itself *injects* a noise class — cached baseline hits return `evidence: "… [cached]"` (src/build-runner/baseline.ts:299–300), so the same verdict differs textually between the uncached first occurrence and every cached replay. PRB's strip classes (ISO-8601 timestamps, UUIDs, `\d+(\.\d+)?(ms|s)\b` durations, `(cached)`/`[cached]`) are exactly the standard volatility set for this evidence shape.

**What we adopt (PRB):** strip-before-collapse-before-cap ordering (AC-06, SCENARIO-014/015); identity anchored on discriminating constants with the both-direction precision/recall pin (AC-08, SCENARIO-018/019); the 11-text replay-to-one-signature test pattern is the grouping-hash regression test (AC-07, SCENARIO-016/017), and `footprint` staying constant mirrors keeping a second stable identity component so a stripped-empty failure string can't cause false merges.

## Q3 — `git stash push -u -- <paths>` as the quarantine primitive: semantics and guards

From git-stash(1) [SRC-09] ⚠️ (all from remembered documentation; not re-verified this session): `git stash push [-u|--include-untracked] [-a|--all] [-m <msg>] [--] [<pathspec>…]` accepts a pathspec **only in `push`** (pathspec support and the `push` subcommand itself landed in Git 2.13); the legacy `git stash save` treats its positional arguments as a *message*, not paths — `git stash save -- path` stashes **everything** with a message "-- path". That is the sharpest "quarantine of everything" footgun: use `push`, never `save`, and always pass a literal `--` separator. The second footgun is the empty pathspec: `git stash push -u` with *no* paths stashes all tracked modifications plus all untracked files — so a harness bug that spreads an empty paths array silently converts a scoped quarantine into a full-worktree stash. Guards: assert the inventory is non-empty before invoking (AC-03 already conditions on non-empty inventory), assert every pathspec element is a non-empty string, and invoke via the repo's existing `execFileSync`-array pattern (`gitLines`, implementation.ts:130–137) so shell quoting can't mangle paths with spaces. Edge exits to treat as *mechanism failure → degrade, never fatal* (SCENARIO-029): a pathspec matching no known file is a `fatal: pathspec … did not match` non-zero exit ⚠️ exact message/exit from memory; paths that match but hold no changes yield "No local changes to save" with no stash created.

Recovery semantics are why stash is the right primitive: a stash entry is a commit graph reachable from `refs/stash`'s reflog (`stash@{N}`), with untracked files captured in a third-parent commit under `-u`. `git stash pop` **only drops the entry on a clean apply** — documented: on conflicts the state is applied but the entry is *not removed*, and you resolve by hand and drop later [SRC-09] ⚠️. Since we never call `drop` or `clear`, a failed recovery cannot lose data: quarantine is reversible by construction (R-N6). Two subtleties: `-u` excludes *ignored* files (only `-a` sweeps them) — the correct choice here, since copied env files and build outputs must survive; and untracked matched files are **removed from the worktree** into the stash, which is precisely the isolation the ACs want. Reflog expiry eventually prunes abandoned stash commits (`gc.reflogExpire`, default ~90 days ⚠️ from memory), so the ledger — not memory of `stash@{0}`'s position, which shifts if anyone else stashes — must carry the stable identifier. `git stash push` prints "Saved working directory…" but not the SHA; capture the ref via `git rev-parse refs/stash` immediately after push (or use the lower-level `git stash create` + `git stash store -m <msg>` pair, which yields the commit SHA directly ⚠️ from memory) to fill AC-12's `stashRef`. No `src/` code currently invokes stash anywhere (verified by search), so the quarantine helper is genuinely new surface with no conflicting precedent; the repo's existing git-invocation style (`gitLines`, baseline.ts's `gitOk`) and kill-switch convention (`SUPER_DEV_NO_SPEC_REUSE` setup.ts:242, `SUPER_DEV_NO_BOOTSTRAP` setup.ts:604) define its shape, and the `.run-lock` bookkeeping (helpers.ts:527+) already serializes per-track runs so `refs/stash` races are out of scope.

**What we adopt (PRC/PRD/Safety):** scoped `git stash push -u -- <paths>` only (AC-03a, AC-09, AC-13 — no `checkout`/`reset`/`clean` anywhere in the mechanism); non-empty-pathspec precondition + `--` separator + `push`-never-`save`; ledger-recorded `stashRef` captured via `rev-parse refs/stash` (AC-10/AC-12); never `drop`/`clear` so pop-conflict preserves the entry; `-u`-not-`-a` and the canonical exclusion set (spec dir, `HARNESS_BOOKKEEPING_FILES` helpers.ts:527–546, `copiedEnvFiles` setup.ts:545–548, phase scope, current-attempt change set) keep the pathspec from ever touching in-scope or owned state (SCENARIO-008/021/028); git-level failure degrades to warning + judge, never fatal (SCENARIO-029).

## Q4 — Baseline-memoization invalidation: cache keys for comparison verdicts

The universal doctrine (Go, Bazel, Docker, `actions/cache`, Turborepo-class hashers): **a memo is sound only if its key covers every input the computation reads**; inputs you cannot enumerate must force bypass. Go's test cache is the cleanest precedent — binary, flags, package file contents, and the *values of environment variables the test reads* all enter the key, and `-count=1` is a documented per-invocation bypass [SRC-07]. Bazel's remote action cache digests command + input contents + declared env, and its documentation's central warning is that actions reading **undeclared** inputs produce cache poisoning [SRC-13] — the classic failure being a stale hit that hands back a verdict computed under a different environment.

This repo's baseline verifier is exactly such a partially-declared computation. Read-verified: the memo key is `JSON.stringify([cwd, mergeBase, language, pm, subjects])` (baseline.ts:296), but the verdict is computed in a detached temp worktree at merge-base whose `node_modules` is **symlinked from the feature worktree** (baseline.ts:244–249, with the code comment "a plain symlink keeps the baseline run cheap"). The feature worktree's dependency state is therefore a causal input to the verdict that is absent from the key; so is the worktree dirt state in the broader sense the requirements care about (the subjects list is *derived* from the feature gate run, and quarantine changes the feature worktree that derivation reads). Stale reuse has three concrete harms, in increasing severity: (1) the post-quarantine re-run inherits a pre-quarantine `regression` verdict, keeping the phase falsely blocked and burning the escalation (cost, since the judge remains arbiter — this is what SCENARIO-006 pins with its observable flip); (2) the poisoning direction — a stale `preexisting` verdict feeding `inScopePass`'s lenient grant would **mask a genuine new regression** (false green), the worst failure mode gates.ts:716–743 was written to prevent; (3) even a semantically-correct hit appends ` [cached]` to the evidence (baseline.ts:299–300), re-injecting the very noise class PRB must strip.

Standard invalidation strategies, in order of cost: (a) **include the environment in the key** — hash the worktree dirt state (e.g. a digest of `git status --porcelain` over quarantined paths) into the cache key, Go-style; (b) **event-driven invalidation** — treat a quarantine as an invalidation event and flush/bypass the memo then (analogous to Docker layer invalidation when a parent input changes); (c) **per-invocation bypass flag** — Go's `-count=1`: a `bypassCache` input on the exactly-one re-run. The repo already ships both hooks: `clearBaselineCache()` (baseline.ts:80–83) and the `CACHE_MAX=100` wholesale clear on overflow (baseline.ts:301). The requirements chose (b)/(c) — "the baseline.ts per-signature memo is invalidated/bypassed for the re-run" (AC-03, SCENARIO-005/006) — which is the minimal deterministic floor for this cycle; folding a dirt-digest into the key (a) is the sound long-term fix and is worth recording as follow-up (it also matches the spec's deferred "environment provenance stamp" embedding item in 00 Part 6).

**What we adopt:** quarantine = invalidation event — the exactly-one post-quarantine re-run must not read a memoized pre-quarantine verdict (AC-03, SCENARIO-006); reuse existing `clearBaselineCache`/bypass plumbing rather than inventing new cache machinery; note key-completeness (dirt-digest in key) as recorded follow-up, not this cycle's surface.

## Q5 — Retry-storm prevention: backoff-and-escalation in orchestrators, and the deterministic floor under LLM judgment

Kubernetes Job is the most explicit fault-classified escalation design. `spec.backoffLimit` (default 6) bounds retries *deterministically by count*; `activeDeadlineSeconds` bounds them by wall clock; and **`spec.podFailurePolicy`** (beta 1.25, GA ~1.31 ⚠️ versions from memory) adds rules of the form `onExitCodes: {containerName, operator: In, values: [42]}` → `action: FailJob` while `onPodConditions: [{type: DisruptionTarget}]` → `action: Ignore` (doesn't consume backoff budget) [SRC-10]. That is PRA in one YAML: a **deterministic classifier over structured exit conditions decides, before any retry, whether this failure class is retryable at all** — unrecoverable-by-retry classes terminate the Job immediately instead of burning the budget. Airflow supplies the anti-windup shape: `retries` + `retry_delay`, `retry_exponential_backoff` growing the delay with `max_retry_delay` capping it (exponential with jitter ⚠️ formula details from memory), plus `execution_timeout` as the per-task wall-clock bound and `on_failure_callback` as the escalation channel [SRC-11]. AWS Step Factors — Step Functions formalizes the two-layer structure as syntax: `Retry` (IntervalSeconds/BackoffRate/MaxAttempts, with jitter strategies) for *transient, classified* error types, and `Catch` routing everything else to a fallback/escalation state [SRC-12]. Retrying and escalating are **different constructs**, not different settings of one construct.

The common architecture across all three: a cheap deterministic layer (count, wall-clock, exit-code class, error-type string) *below*, and intelligent/human judgment *only at the escalation boundary* — none of them puts a model in the retry-decision loop. That is exactly this cycle's NFR-1: the classification floor is pure TypeScript over `BuildGateResult` + own-scope booleans; the judge (LLM) is the arbiter above it, invoked at *first occurrence* of an un-actionable class (AC-04) — the andon/`FailJob` pattern — and always carrying `escalate-now` (already unioned into every `allowedRoutes` offer, judge.ts:230). Two deliberate deviations from the classic orchestrators, both justified by this system's economics: (1) **backoff delay is useless here** — attempts cost tens of minutes and the failure class is either environmental (retrying later without changing state is F-3's "pure cost bet": nothing changed) or product (feedback changes each attempt, making delay counterproductive); (2) the K8s `Ignore` class (doesn't consume budget) has no analog because there is no external scheduler to ignore for — the equivalent is PRB's *identical-normalized-signature refusal* (second identical occurrence → escalate, never a third spawn, AC-07/SCENARIO-017), which subsumes backoff's purpose: it detects "nothing changed since the last bet" and refuses to re-bet. The one-re-run quarantine budget (AC-03) is the bounded retry *with a state change* — the only rational retry per F-3.

**What we adopt (PRA/PRB):** deterministic floor under judgment (NFR-1, AC-01); first-occurrence escalation for classes the current actuator cannot fix — the `FailJob` analog — via `runJudge` with `["fix-environment"]` (AC-04, SCENARIO-010/011/012); identical-signature refusal as the anti-windup replacement for backoff (AC-07, R-S6); exactly-one state-changing retry (quarantine+re-gate) as the only automatic re-bet (AC-03); wall-clock protection remains the existing attempt/cancel machinery, unchanged.
