# Debug Analysis: Specialists silently fail to inherit an extension-sourced model: ambient-extension suppression (determinism) starves the child's fresh provider registry

- **Date**: 2025-01-01

---

## Summary

The recently-added model-inheritance feature passes the parent session's `ctx.model` object to spawned specialists — correctly, for built-in providers. But it SILENTLY FAILS whenever the user's active model comes from an EXTENSION-REGISTERED provider (a custom `pi.registerProvider(...)` extension, the llama.cpp router, etc.). Root cause: both specialist backends DELIBERATELY suppress ambient extensions for determinism + isolation — the session backend sets `noExtensions: true` at `src/session-agent.ts:487`, and the subprocess backend pushes `--no-extensions` for every non-browser agent at `src/pi-spawn.ts:276`. Extension-registered providers only exist once the owning extension LOADS; with extensions suppressed the child's fresh `modelRuntime`/settings layer has no registration for that provider id. So when the child tries to resolve the inherited model (the `provider/id` string on the subprocess path, or the model object on the session path) it cannot bind auth/streaming for that provider and falls back to the SDK/settings default — "inherit the parent's model" is a no-op for extension-sourced models with no error surfaced. The bug is invisible in the default model stack (Anthropic/OpenAI built-ins) and in browser-capable agents (which already OMIT `--no-extensions`), which is why it went undetected. This is a deliberate-design conflict, not a coding mistake — the fix is an env-var opt-in `SUPER_DEV_INHERIT_EXTENSIONS` (default OFF → byte-identical to today) that lets users whose model stack depends on an extension provider turn ambient extension loading back on for specialists, at the cost of determinism.

## Hypotheses

- H1 (HIGH, ~70%) — Extension suppression starves the provider registry. Prediction: with the opt-in OFF, a specialist whose inherited model's provider is extension-registered CANNOT resolve it (silent fallback to settings default), while a BROWSER-capable specialist — which already omits --no-extensions — DOES resolve it correctly. This differential is the falsifiable signature. Confirmed by code: both suppression points exist (session-agent.ts:487 noExtensions:true, pi-spawn.ts:276 if(!browser) push --no-extensions) and both inheritance paths are wired (session passes inheritedModelObject straight to createAgentSession; subprocess qualifies provider/id into --model).
- H2 (MEDIUM, ~20%) — The inherited model reference is malformed (bare id / missing provider), so resolution fails regardless of extensions. Prediction: even WITH extensions loaded, the child still can't resolve. FALSIFIED by inspection: pi-spawn.ts builds `${provider}/${id}` (always qualified, never bare — explicitly closes the opencode bare-id mis-resolution noted in the comment), and the session path passes the whole model object. So the ref is well-formed; the failure is resolution-side, not ref-side.
- H3 (LOW, ~8%) — A resourceLoader.reload() ordering/timing race makes the inherited model resolve before the provider is available. Prediction: the failure is non-deterministic or ordering-dependent. FALSIFIED: in session-agent.ts the loader is constructed and reloaded BEFORE model resolution, and the model resolution itself is a synchronous try/catch that simply passes the object through — no async gap to race on. The subprocess path is a fresh process, so no in-memory race is possible at all.
- H4 (LOW, ~2%) — pi 0.82.x SDK regression in provider scoping. Prediction: the bug reproduces on built-in providers too. FALSIFIED: the task states (and tests confirm) built-in-provider inheritance works; only extension providers fail.

## Root Cause

Two intentional, separately-correct design decisions collide: (1) model inheritance ships the parent's full `ctx.model` to each specialist (session backend: `opts.inheritedModelObject` passed directly to `createAgentSession` at src/session-agent.ts ~line 511-514; subprocess backend: qualified `${provider}/${id}` pushed as `--model` at src/pi-spawn.ts ~line 286-289); and (2) both specialist backends DELIBERATELY suppress ambient extension discovery for determinism/isolation — session: `noExtensions: true` at src/session-agent.ts:487; subprocess: `if (!browser) args.push(\"--no-extensions\")` at src/pi-spawn.ts:276. An extension-registered provider (custom `pi.registerProvider(...)`, llama.cpp router, etc.) only enters the child's provider registry WHEN its owning extension LOADS. Under suppression the provider id is unregistered in the child's fresh resolution layer, so binding auth/streaming for the inherited model fails and the child silently falls back to the SDK/settings default (best-effort, no-throw — the session path is wrapped in try/catch that falls through to inheritedModelObject; the subprocess path relies on pi's own no-crash fallback). The failure is silent (no exception, no warning) and only manifests for extension-sourced providers — which is why the existing test suite, run against built-in providers, stayed green. Browser-capable agents (which already OMIT --no-extensions) are the confirming control: they load extensions, so their providers ARE registered, so inheritance works for them. The fix is not to remove suppression (that would break determinism/isolation guarantees), but to add an opt-in escape hatch: `SUPER_DEV_INHERIT_EXTENSIONS` (default OFF → byte-identical current behavior). Wire it into both suppression points — session: `noExtensions: !inheritExtensions()`; subprocess: `if (!browser && !inheritExtensions()) args.push(\"--no-extensions\")` — leaving the inline safety factory and the inheritedModelObject path untouched.

## Reproduction Steps

- SETUP a provider that ONLY exists via an extension: install/enable a global pi extension that calls `pi.registerProvider("llamacpp", factory)` (or use the llama.cpp router extension), and set the active model to `llamacpp/<some-model>` (or export SUPER_DEV_MODEL=llamacpp/<id>).
- REPRO (default/OFF): run any super-dev goal that spawns a non-browser specialist (e.g. an implementation or research stage). Inspect the spawned `pi` argv (buildSpawnArgs output) — confirm `--no-extensions` IS present AND `--model llamacpp/<id>` IS present. The child process starts, cannot resolve the `llamacpp` provider (no extension loaded it), and silently runs on the settings default model instead of the inherited one — no error, the stage just runs on the wrong model.
- DIFFERENTIAL CONTROL: run the same goal but with the spawned specialist being a BROWSER-capable agent (BROWSER_AGENTS). It omits --no-extensions → loads ambient extensions → the llamacpp provider registers → the inherited model resolves correctly. Same code path, opposite result, proves the cause is extension suppression, not the inheritance ref.
- CONFIRM root cause statically: grep src/session-agent.ts:487 for `noExtensions: true` and src/pi-spawn.ts:276 for `if (!browser) args.push("--no-extensions")` — both gate ambient extension loading, and both sit upstream of model resolution.
- VERIFY FIX (after implementation): set SUPER_DEV_INHERIT_EXTENSIONS=1, repeat step 2 — `--no-extensions` is now ABSENT for the non-browser specialist (and the session loader uses `noExtensions: false`), the extension loads, the provider registers, and the inherited model resolves identically to the browser-agent control. Toggle it back to 0/false/unset and confirm byte-identical-to-today behavior returns (focused pi-spawn unit tests cover --no-extensions present-when-OFF / absent-when-ON / never-for-browser; inheritExtensions() truthy/falsy parsing test covers 1|true|yes|on vs unset/0/false/empty/garbage).
