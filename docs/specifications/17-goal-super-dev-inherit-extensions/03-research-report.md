# Research Report: SUPER_DEV_INHERIT_EXTENSIONS opt-in: external grounding for pi extension/provider suppression toggling

- **Date**: 2026-07-28
- **Author**: super-dev:research-agent

---

## Summary

Online research against the pi-coding-agent 0.82.1 source, docs, and issue tracker fully confirms the spec's diagnosis and prescribed wiring. (1) The provider-registration mechanism is real and extension-coupled: `pi.registerProvider(...)` pushes to `runtime.pendingProviderRegistrations`, which are only flushed into the model registry by `bindCore()` after the extension factory runs (loader.ts). So when ambient extensions are suppressed, no provider is ever registered and the child's model runtime cannot resolve an extension-sourced model — it degrades to the settings default (sdk.md's fallback chain), exactly the silent-failure the opt-in closes. (2) `DefaultResourceLoader`'s `noExtensions` is the precise knob: in `reload()`, `extensionPaths = noExtensions ? cliPaths : merge(cliPaths, ambient)`; the inline `extensionFactories` (safety factory) load via a separate `loadExtensionFactories(runtime)` call that is INDEPENDENT of `noExtensions` — confirming AC-03's claim that the safety factory stays either way. (3) `--no-extensions` is the genuine CLI flag (introduced in PR #524), and issue #776 documents that its 'extensions not loaded' contract had a bug in 0.46/0.47 (empty result fell through to discovery) that was fixed by passing the empty result through; the repo's ^0.82.1 is far past the fix, so the default-OFF byte-identical guarantee holds, but the contract has historically been version-fragile. (4) The prescribed boolean parser `/^(1|true|yes|on)$/i` with `.trim()` is the idiomatic best practice: the canonical Node.js pitfall is `Boolean("false")===true` (every non-empty string is truthy), and the durable fix is an explicit allowlist regex/enum parsed once at the boundary — matching the existing SUPER_DEV_* env-read pattern and introducing zero new dependencies. No contradictions with the spec were found; all four AC-wiring decisions are validated as minimal and correct.

## Options Considered

### Boolean env-var parser: keep the prescribed allowlist regex `/^(1|true|yes|on)$/i` + `.trim()` (no new dependency)

Grounded in the well-documented Node.js pitfall that `Boolean(process.env.X)` is `true` for ANY non-empty string including `"false"`, `"0"`, `"no"` (SRC-07). The durable fix recommended across the ecosystem is an explicit token allowlist parsed once at the boundary — exactly the spec's regex — which is case-insensitive and `.trim()`-tolerant (covering SCENARIO-002's padded/mixed-case inputs) and returns `false` for unset/empty/`0`/`false`/garbage (SCENARIO-003/SCENARIO-016). Alternatives like envalid's `bool()` or a Zod `boolish` enum exist (SRC-07) but would add a dependency and a config module for a SINGLE env read, breaking parity with the existing inline `SUPER_DEV_MODEL`/`SUPER_DEV_THINKING`/`SUPER_DEV_BACKEND` reads in pi-spawn.ts. The short-circuit `Boolean(env && regex.test(env.trim()))` also correctly yields `false` when the var is unset. RECOMMEND: implement exactly as prescribed; it is the idiomatic, zero-dependency, boundary-parsed best practice. Serves AC-01, SCENARIO-001/002/003/016.
### Session-backend wiring: `noExtensions: !inheritExtensions()` on the `DefaultResourceLoader` (as prescribed)

Directly grounded in resource-loader.ts (SRC-04): the constructor stores `noExtensions` (default `false`) and `reload()` computes `extensionPaths = this.noExtensions ? cliEnabledExtensions : this.mergePaths(cliEnabledExtensions, enabledExtensions)`. For a specialist (no `-e` CLI paths) this means `noExtensions:true` → empty path list → no ambient extension load → no `registerProvider` calls (SRC-05), and `noExtensions:false` → ambient global (`<agentDir>/extensions/`) + project (`.pi/extensions/`) extensions load and their providers register. Critically, the inline `extensionFactories` are loaded by a SEPARATE `loadExtensionFactories(extensionsResult.runtime)` call that runs regardless of `noExtensions`, so the safety factory stays loaded in both states — confirming AC-03/SCENARIO-007/008. The prescribed `!inheritExtensions()` toggle is therefore the minimal change that flips exactly the ambient-discovery branch. RECOMMEND: implement as prescribed. Serves AC-03, SCENARIO-007/008.
### Subprocess wiring: `if (!browser && !inheritExtensions()) args.push("--no-extensions")` (as prescribed)

`--no-extensions` is the genuine pi CLI flag (introduced in PR #524, SRC-03) that skips all ambient extension discovery/load. Issue #776 (SRC-02) confirms its semantics: when set, extensions from `~/.pi/agent/extensions/` and `.pi/extensions/` are NOT loaded (after the 0.47 fix). The existing `!browser` carveout is required because browser-capable agents must load pi-browser-cdp and already omit the flag (AC-04). Adding `&& !inheritExtensions()` is the minimal change preserving byte-identical OFF behavior (`!browser` alone still pushes the flag) and only suppressing it for non-browser agents when opted in. RECOMMEND: implement exactly as prescribed; do NOT alter the browser branch. Serves AC-02, AC-04, SCENARIO-004/005/006.
### Default-OFF isolation guarantee + version-fragility caveat for the trade-off comment

The byte-identical-OFF requirement (AC-09, SCENARIO-014) rests on `--no-extensions`/`noExtensions:true` reliably suppressing ALL extension load. Issue #776 (SRC-02) shows this contract has historically been fragile: in 0.46.0/0.47.0 an empty extension result was treated as undefined and fell through to the discovery branch, so extensions loaded anyway. The fix (pass the empty result through) landed well before ^0.82.1, so the OFF behavior is sound on the target version — but this is a VERSION-DEPENDENT guarantee. The AC-05 trade-off comment should therefore state not only the determinism loss when opted IN (child loads ALL user extensions, potential self-include of super-dev, though specialists take no user input so no self-trigger) but implicitly relies on the flag's stability. RECOMMEND: write the comment as prescribed; additionally note in the implementation stage that any future pi downgrade below the #776 fix would silently break the OFF guarantee — a low-severity version-pin note, not a blocker.

## Open Issues

- ISS-01 (LOW, version-pin): The default-OFF byte-identical guarantee depends on the `--no-extensions`/`noExtensions:true` 'extensions fully suppressed' contract being intact. Issue #776 shows this contract was broken in 0.46/0.47 and fixed before ^0.82.1; the fix is present on the target version, so this is NOT a blocker, but the AC-05 trade-off comment is the right place to acknowledge the opt-in's determinism loss and the implementation stage should note that a pi downgrade below the #776 fix would silently re-break OFF behavior.
- ISS-02 (INFO, non-goal reaffirmed): Research surfaced that pi also exposes provider config via `models.json` and `--api-key`/`resolveCliModel` resolvers (sdk.md) which are NOT extension-gated. The spec correctly scopes the opt-in to extension-registered providers only (e.g. llama.cpp router, corporate proxies via `pi.registerProvider`); models supplied purely through `models.json` do not need this opt-in. No change to scope recommended — flagging only so the implementation stage does not over-broaden the change.
- ISS-03 (INFO, out-of-scope): The requirements Open Question about documenting `SUPER_DEV_INHERIT_EXTENSIONS` in README/docs (parity with other SUPER_DEV_* vars) is not addressed by external research; it remains a product decision for the human. Research confirms other SUPER_DEV_* env vars are README-documented, so parity would be consistent, but AC-07 only requires the CHANGELOG entry.
