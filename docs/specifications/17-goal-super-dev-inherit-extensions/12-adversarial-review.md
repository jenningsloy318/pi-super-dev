# Adversarial Review: Adversarial Review — SUPER_DEV_INHERIT_EXTENSIONS opt-in (spec-17)

- **Date**: 2025-01-22
- **Reviewer**: super-dev:adversarial-reviewer
- **Verdict**: CONTEST

---

The change is small, additive, default-OFF, and byte-identical to the baseline when the env var is unset — exactly as the intent demands. The `inheritExtensions()` helper is correct (leading `Boolean(env && ...)` short-circuits `.trim()` on undefined, so malformed input never throws), the subprocess wiring is a clean one-liner, the browser-agent invariant is preserved, the CHANGELOG anchor satisfies both contract tests, and all 80 targeted tests pass with typecheck clean. Both backends flip in lockstep via a single shared helper, so there is one source of truth and no new coupling axis or deadlock surface.

However, the review surfaces quality concerns that warrant an author response rather than an unconditional PASS: (1) the DEFAULT backend (session) — the highest-traffic path — has NO automated assertion on its `noExtensions` wiring, while the subprocess path got the full matrix; the AC's escape clause sanctioned this, but it leaves the default path guarded only by a human-read comment. (2) The CHANGELOG bullet is a ~400-word run-on that violates the spec's "concise" acceptance criterion and Keep-a-Changelog norms. (3) A load-bearing safety claim ("the pipeline cannot self-trigger even with super-dev loaded as an ambient extension") is asserted as fact across all three comment sites with zero verification. (4) Pipeline-wide blast radius and token/context-inflation cost are under-documented. None rise to REJECT (no production failure, data loss, or security breach); the implementation is functionally correct and safe to ship, but the coverage asymmetry and over-documentation should be addressed.

### AR-01: Default session-backend wiring has no automated test — only the subprocess path does

- **Severity**: medium
- **Lens**: Architect
The DEFAULT backend is `session` (src/workflow.ts:206 `?? "session"`; src/types.ts:298 lists both), yet only the subprocess backend's wiring has a test matrix (tests/pi-spawn.test.ts asserts `--no-extensions` presence/absence across opt-in states for non-browser vs browser agents). The session backend's `noExtensions: !inheritExtensions()` (src/session-agent.ts:497) — the highest-traffic path — is guarded only by the `inheritExtensions()` unit test and a human-read comment. The AC's escape clause ('if the loader construction is unit-testable in isolation, add a parallel assertion; otherwise the unit test + documented wiring is sufficient') technically sanctioned this, but `DefaultResourceLoader` IS constructible in isolation: the code already constructs it with cwd/agentDir/settingsManager/noExtensions and only calls `.reload()` afterward. A test can assert the constructed loader's `noExtensions` value (or spy the constructor arg) across opt-in states WITHOUT calling `.reload()`, so the escape clause's precondition does not actually hold. Risk: a future refactor of src/session-agent.ts:497 silently regresses the byte-identical baseline on the default path with no test catching it. Recommend a cheap assertion on the constructed loader's `noExtensions` value for unset/truthy/falsy env states. [UNCERTAIN only in that it depends on whether `DefaultResourceLoader` exposes the option post-construction; if not, a constructor-arg spy suffices.]
### AR-02: CHANGELOG `### Added` bullet is ~400 words — violates the spec's 'concise' criterion and Keep-a-Changelog norms

- **Severity**: medium
- **Lens**: Minimalist
AC-07 and the task spec asked for a 'concise `[Unreleased]` CHANGELOG.md entry (### Added) summarizing the opt-in.' The added bullet (CHANGELOG.md line 10) is a single ~400-word run-on paragraph that re-states AC-01..AC-07, SCENARIO-001..016, the implementation mechanics (qualified provider/id, resolveExplicitSessionModel, noExtensions wiring), the zero-ANSI/print-json-rpc-headless contract, and the test-harness reuse — none of which belong in a user-facing changelog. Keep-a-Changelog `### Added` entries are meant to be human-readable summaries of user-visible behavior. This reads like a spec-coverage manifest. Recommend trimming to ~2 sentences: what the opt-in does + the default-OFF byte-identical guarantee + the env var name. (The spec-15 Fixed entry is also long, but this one is materially longer and the verbosity pattern should not compound across specs.)
### AR-03: Load-bearing safety claim 'the pipeline cannot self-trigger' is asserted as fact with no test

- **Severity**: medium
- **Lens**: Skeptic
The helper doc (src/pi-spawn.ts:196-204) and BOTH wiring comments (src/session-agent.ts:490-496, src/pi-spawn.ts:291-301) assert that loading super-dev ITSELF as an ambient extension cannot re-trigger the pipeline because 'spawned specialists receive no interactive user input, so the pipeline still cannot self-trigger even with super-dev loaded.' This is a load-bearing safety justification for shipping the opt-in, yet nothing verifies it. A re-entrancy/extension-registration interaction is plausible: super-dev as an ambient extension registers a `super-dev` command, tool, or middleware, and the specialist's single turn could in principle dispatch it. The claim is PROBABLY true (specialists run one fixed-prompt turn with no slash-command dispatch path), but it is an unverified assertion presented as a guarantee. Recommend either (a) softening the language from guarantee ('cannot self-trigger') to calibrated expectation ('is not expected to self-trigger; not regression-tested'), or (b) adding a smoke test that a specialist spawn with the opt-in ON completes one turn without pipeline re-entry. [UNCERTAIN — depends on pi's extension/extension-command dispatch semantics for non-interactive single-turn agents.]
### AR-04: Pipeline-wide blast radius and token/context-inflation cost are under-documented

- **Severity**: low
- **Lens**: Skeptic
`SUPER_DEV_INHERIT_EXTENSIONS` is a single global env var that applies to EVERY specialist in EVERY stage — including code-writing agents (implementer/tdd-guide) that never touch model resolution. Ambient extensions can inject system-prompt text, tools, and MCP servers, materially inflating the child's context/token budget and slowing spawns; the comments name only 'provider/tool registration' as the cost. For a user who sets the flag for ONE provider reason, every stage pays the full ambient-extension load. Additionally, the subprocess backend retains the `--tools` allowlist as a remaining ACTIVE-tool guard, but the session backend has no analogous ACTIVE-tool allowlist called out in the change — so the session path's tool surface broadens more. Not a blocker (explicit opt-in, documented determinism trade-off), but recommend (a) noting the concrete token-budget/context-inflation cost in the helper doc, and (b) scoping the opt-in's intended use to model-stack-dependent users rather than general ambient-extension loading.
### AR-05: Triplicated trade-off prose + duplicated contract-test scaffolding

- **Severity**: low
- **Lens**: Minimalist
The same determinism/isolation trade-off paragraph is restated near-verbatim in THREE places: the helper doc (src/pi-spawn.ts:196-204), the session-agent comment (src/session-agent.ts:481-497), and the buildSpawnArgs comment (src/pi-spawn.ts:291-302). Recommend DRY-ing to a single canonical statement in the helper doc with one-line back-references at the two wiring points. Separately, tests/changelog-unreleased-spec17.test.ts (120 lines) copy-pastes `unreleasedSection()` and `BOLD_BULLET_ANCHORED` verbatim from tests/changelog-unreleased-spec15.test.ts rather than extracting a shared `tests/changelog-helpers.ts`; this is a pre-existing pattern, but each new spec deepens the copy. A shared helper would collapse the spec-17 test to ~30 lines of unique assertions. Low, but worth flagging since the test scaffolding will keep duplicating per spec.
### AR-06: Research-agent comment states isolation as an invariant, but it only holds in the baseline

- **Severity**: low
- **Lens**: Skeptic
The buildSpawnArgs comment (src/pi-spawn.ts:294-301) says 'Research still loads ONLY its two extensions explicitly via `-e <path>` ... so no other global extension is pulled in.' That is true ONLY when the opt-in is OFF. With `SUPER_DEV_INHERIT_EXTENSIONS=1`, research agents are non-browser → they ALSO drop `--no-extensions` → they DO pull in every ambient extension alongside their two explicit ones. The sentence reads as a constant invariant but is baseline-conditional; a reader opting in could misunderstand research-agent isolation. Recommend qualifying to 'in the baseline (opt-in OFF); with the opt-in ON, research agents also load ambient extensions.' Low — documentation accuracy, not behavioral.
